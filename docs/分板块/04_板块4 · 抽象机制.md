## 板块4 · 抽象机制：方法集、隐式接口、组合与泛型

### 4_1 核心机理与关键概念

板块3 把数据摆平，板块4 决定"谁可以操作这些数据"。Go 的抽象只有三件工具，但组合方式极有讲究。

方法集规则：类型 `T` 的方法集只含值接收者方法；`*T` 的方法集含值接收者与指针接收者方法。接口实现是隐式的，不需要声明，编译器按方法集自动匹配——好处是调用方与实现方彻底解耦，代价是"到底实现了没有"要到编译期才暴露。

因此惯用做法是写一行编译期断言 `var _ Storer = (*FileStore)(nil)`。

接口设计遵循"越小越好"：调用方定义自己需要的最小接口，实现方不必知道自己被哪个接口消费。空接口与 `any` 只用于真正的异构容器，滥用会把类型错误推迟到运行时。组合优于继承：把小结构体嵌入大结构体，方法被提升，但被嵌入者不知道自己被谁嵌入。

泛型则用于"算法相同、类型不同"的场景，用约束描述类型集合，而不是用 `any` 加类型断言硬凑。

```text
  调用方                 契约层                 实现方
  +--------+          +----------+          +-----------+
  | Handler| --需要--> | interface| <--隐式-- | MemoryStore|
  |        |          | Get/Put  |          | FileStore  |
  +--------+          +----------+          +-----------+
       定义最小接口          无 import 依赖        不知道被谁用
```

接口值内部是两个字：动态类型信息与动态值。两个字都为空时接口才等于 nil；把一个 nil 指针赋给接口，类型字非空而值字为空，接口整体并不等于 nil。这就是"函数里明明返回了 nil，调用方却判不空"的经典事故来源。

正确口径是：返回接口时要么返回真正的 nil 接口，要么返回带确定值的接口，不要把 `(*T)(nil)` 交给调用方去判空。

| 表达式 | 类型字 | 值字 | 与 nil 比较 |
| --- | --- | --- | --- |
| `var x Storer` | 空 | 空 | 相等 |
| `x = (*FileStore)(nil)` | 非空 | 空 | 不相等 |
| `x = &FileStore{}` | 非空 | 非空 | 不相等 |

泛型约束的本质是类型集合，不只是"能调用哪些方法"的清单。约束接口里可以写方法，也可以并列多个类型、用近似元素表示"底层类型相同的所有具名类型"；编译器据此在实例化时检查实参是否落在集合内。约束写得越窄，类型推断越明确，误用越早在编译期暴露。

| 约束写法 | 含义 | 适用场景 |
| --- | --- | --- |
| `any` | 全体类型 | 仅异构容器，不用于承载算法 |
| `comparable` | 可比较类型集合 | 作 map 键、去重、相等判断 |
| 整型族的近似元素并集 | 底层类型属于该族的所有具名类型 | 数值算法按族复用 |
| 接口内声明方法 | 满足该方法集的类型集合 | 结构化能力约束 |

方法集（method set）与类型集合是两条不同的判定链：前者决定"这个类型是否满足某接口"，后者决定"这个类型能否实例化某泛型函数"。评审时把两者分开问，能省掉大半"为什么编译不过"的往返。

### 4_2 可落地操作清单

第1步：定义一个只含两个方法的 `Storer` 接口，再写内存版与文件版两个实现，都不 import 调用方包。
第2步：给两个实现各加一行编译期接口断言，然后故意删掉一个方法，观察编译报错位置。
第3步：把值接收者改成指针接收者，验证 `T` 不再满足接口而 `*T` 满足，把结论记进反例卡。
第4步：写一个消费方函数，参数用只含 `Get` 的窄接口，验证它也能接收 `Storer` 实现。
第5步：用嵌入组合出一个带日志能力的包装器，不修改原实现一行代码，只在外层加计数。
第6步：把一段重复的类型转换逻辑改写成泛型函数，约束用 `comparable` 或自定义约束，跑 `go vet` 确认无告警。

### 4_3 场景笔记法：接口契约与可替换性记录

接口类笔记的价值在于"换实现时不翻旧账"，所以用契约卡把隐含约定显性化。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明消费方需要什么能力、当前有哪几个实现 |
| 预期 | "换掉实现后调用方零改动，测试全绿；删方法时编译期即报错" |
| 动作 | 贴接口定义、编译期断言行、以及替换实现那一行改动 |
| 观察 | 粘贴编译报错首行或 `PASS` 输出，保留包名与行号 |
| 判定 | 替换成功且无调用方改动记"通过" |
| 迁移 | "新实现先补断言再写逻辑；接口超过三个方法就先质疑拆分" |

实用补充：为每个接口额外记两条"契约外约定"——并发安全与否、错误是否可重试。它们不会写进类型系统，却最常在生产里出事，必须落在笔记里。

### 4_4 案例小故事：一个二十方法接口引发的僵局

某服务早期图省事，把"用户存储"定义成一个二十多个方法的胖接口，缓存层、数据库层、测试桩都去实现它。后来要加一个只读的报表模块，按理只需要一个查询方法，却被迫实现全部二十几个方法，测试桩里塞满了 `panic("未实现")`。

更麻烦的是，任何一次存储层改动都要同步改三套桩，改到后来没人敢动。

重构只做了两件事：调用方各自定义窄接口，报表模块只声明一个 `Reader`，入口处用 `var _ Reader = (*DBStore)(nil)` 兜底；胖接口被拆成读、写、管理三组，实现方按需组合。测试桩从二十几个方法缩到一个。

有意思的是，编译期断言在重构第二天就抓到一次事故：有人把 `Get` 的接收者从指针改成值，导致某处赋值不再满足接口，CI 当场变红，而不是等到运行时空指针。团队把这一天记成契约卡的范例，标题是"让编译器替你守约定"。

### 4_5 实用验证：命令、预期与判定

第1步：把下面这段保存为 `verify_interface.go`，执行 `go run verify_interface.go`。编译期断言行就在文件里，删掉 `Get` 方法再跑一次即可看到编译器报错。

```go
package main

import "fmt"

type Reader interface {
    Get(key string) (string, error)
}

type MemoryStore struct{ m map[string]string }

func (s *MemoryStore) Get(key string) (string, error) {
    return s.m[key], nil
}

var _ Reader = (*MemoryStore)(nil)

func read(r Reader, key string) {
    v, err := r.Get(key)
    fmt.Printf("key=%s value=%q err=%v\n", key, v, err)
}

func main() {
    s := &MemoryStore{m: map[string]string{"a": "one"}}
    read(s, "a")
}
```

第2步：在完整项目里执行下列门禁命令。

```bash
go build ./...
go test ./...
go vet ./...
```

预期：程序输出 `key=a value="one" err=<nil>`。

把 `Get` 的接收者从 `*MemoryStore` 改成 `MemoryStore` 后，`var _ Reader = MemoryStore{}` 与 `var _ Reader = (*MemoryStore)(nil)` 两条断言都能通过；

反过来，保留指针接收者却把断言改成值类型 `var _ Reader = MemoryStore{}`，编译应立刻报 `does not implement`；把 `read` 的参数换成只含 `Get` 的更窄接口，调用方无需改动，测试仍全绿。

判定：做三次主动破坏——删方法、改接收者、把接口加宽到含 `Put`，分别记录编译报错首行。三次都能被编译期或测试抓住，记"通过"；若某次破坏悄无声息，说明断言或测试覆盖有缺口，先补再往下走。

### 4_6 常见误区与进阶钩子

「1」误区：在实现方包里定义接口。应由消费方定义，实现方只提供方法。
「2」误区：用 `any` 承载业务数据，再到处做类型断言。优先用泛型约束把类型集合说清楚。
「3」误区：以为嵌入就是继承。被嵌入者无法感知外层，也不存在方法覆盖的动态分派语义。
「4」误区：接口里塞入"顺便可能用到"的方法。每多一个方法，所有实现与测试桩都要多背一份债。
「5」进阶钩子：写一个带自定义约束的泛型 `Map` 函数，用 `go doc constraints` 查可用约束，再尝试让一个不满足约束的类型传入，把编译报错记成反例卡。
