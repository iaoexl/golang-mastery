## 板块7 · 标准库实战：流式 I/O、编码、服务与时间

### 7_1 核心机理与关键概念

板块6 把项目立起来，板块7 往里填真实能力。标准库的设计有一个贯穿始终的套路：用小接口拼大能力。

`io.Reader` 与 `io.Writer` 各自只有一个方法，却能被 `bufio`、`io.Copy`、`gzip`、`os.File`、`bytes.Buffer`、`net.Conn` 同时实现，于是"从任意来源读、往任意去处写"变成一行 `io.Copy`。

`encoding/json` 靠结构体标签与 `Marshaler`/`Unmarshaler` 接口工作，注意时间、数值精度与未知字段这三个高频坑。

`net/http` 的服务端把"路由—处理器—中间件"压成 `http.Handler` 一个接口，客户端必须显式设置超时，否则默认无超时会拖垮连接池。`time` 用 `Duration` 做算术、用 `Timer`/`Ticker` 做调度，涉及墙上时间时务必显式带位置信息。

`path/filepath` 负责跨平台路径拼接，别用字符串硬拼。

```text
  任意来源              io 管道                任意去处
  +--------+      +----------------+      +----------+
  | os.File|      | bufio.Scanner  |      | os.Stdout|
  | net.Conn| --> | io.Copy        | -->  | bytes.Buffer|
  | strings|      | gzip.Reader    |      | http.Response|
  | Reader |      | json.Decoder   |      | Writer   |
  +--------+      +----------------+      +----------+
        只依赖 Read/Write 两个方法，不依赖具体类型
```

### 7_2 可落地操作清单

第1步：用 `io.Copy` 把文件流写进 `bytes.Buffer`，再用 `bufio.Scanner` 逐行读回，确认两者都不需要把整份数据一次性载入。
第2步：用 `json.Decoder` 从一个流里连续解多个对象，对比 `json.Unmarshal` 一次性解整个字节片的差别。
第3步：定义带 `json` 标签的结构体，覆盖缺省值、时间字段、未知字段三类输入，分别打印结果。
第4步：写一个 `http.Handler` 提供健康检查与一个业务接口，用 `httptest.NewRecorder` 直接测处理器，不启端口。
第5步：给 `http.Client` 显式设置 `Timeout`，并给服务端设置读写超时，验证慢请求会被切断。
第6步：用 `filepath.Join` 与 `time.ParseInLocation` 各改一处硬编码，跑 `go vet` 确认无告警。

### 7_3 场景笔记法：I/O 联调与接口契约留痕

I/O 类场景的坑多半在"边界数据"上，笔记要按输入形态分栏，而不是按函数名分栏。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明数据来源（文件、网络、内存）、数据规模、是否流式 |
| 预期 | "大文件不整份载入；未知字段被忽略或按约定报错；慢请求在超时内返回" |
| 动作 | 贴出 Reader/Writer 组合链与超时设置的那几行 |
| 观察 | 粘贴内存峰值、返回状态码、耗时、解码后的字段值 |
| 判定 | 三类边界输入（空、超大、畸形）全部符合预期记"通过" |
| 迁移 | "凡接外部数据先写畸形输入用例；凡发外部请求先写超时用例" |

实用补充：给每个外部接口建一张"字段契约表"，记录字段类型、是否可空、缺省语义。JSON 的零值与"字段缺失"在 Go 里常常长得一样，这张表是区分它们的唯一依据。

### 7_4 案例小故事：一个没设超时的客户端拖垮整池

某内部服务偶发请求堆积，重启就好，过一阵又犯。日志里没有 panic，也没有慢 SQL。最后在连接层面找到原因：调用下游的 `http.Client` 是零值直接用的，没设 `Timeout`；下游某次抖动后有一批连接长期挂着不返回，连接池被占满，后续请求全在等。

修复很小：客户端显式设置 `Timeout`，并用带 `context.WithTimeout` 的请求把超时沿调用链传下去；服务端补上读写超时；再加一个用 `httptest.NewServer` 故意不响应的测试用例，断言调用方会在约定时间内返回。

值得一提的是，这个测试用例后来在另一次改动里又救了场：有人把超时改成一个极大的值，测试立刻变红。团队把用例命名成"慢下游"，并在笔记里写下一句判据：任何外部调用，都要能在测试里被"假装不响应"验一遍。这条判据在板块10 的系统边界里被扩展到重试与优雅关闭。

### 7_5 实用验证：命令、预期与判定

第1步：把下面这段保存为 `verify_timeout.go`，执行 `go run verify_timeout.go`。假服务会故意慢 2 秒，用来检验客户端超时是否真的生效。

```go
package main

import (
    "fmt"
    "net/http"
    "net/http/httptest"
    "time"
)

func main() {
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        select {
        case <-r.Context().Done(): // 客户端超时后这里立刻被唤醒
            return
        case <-time.After(2 * time.Second):
            w.WriteHeader(http.StatusOK)
        }
    }))
    defer srv.Close()

    client := &http.Client{Timeout: 200 * time.Millisecond}
    start := time.Now()
    resp, err := client.Get(srv.URL)
    if resp != nil {
        resp.Body.Close()
    }
    fmt.Printf("耗时=%v 是否按超时返回错误=%t err=%v\n",
        time.Since(start).Round(time.Millisecond), err != nil, err)
}
```

第2步：在完整项目里执行下列门禁命令。

```bash
go test -run TestIO -v ./...
go vet ./...
go test -race ./...
```

预期：程序打印 `是否按超时返回错误=true`，耗时约 200 毫秒；把 `Timeout` 字段删掉后重跑，耗时约 2 秒且该值翻转为 false。门禁侧 `vet` 与 `-race` 零告警；

按 7_2 第1步与第3步补的 `io.Copy` 大文件用例、畸形 JSON 用例，分别满足"内存峰值不随文件大小线性增长"与"明确报错而非半初始化结构体"。

判定：三项全中记"通过"。补一道对照验证：把 `Timeout` 去掉再跑同一下游，调用应明显挂住直到假服务返回；能看到"挂住"与"按时返回"的差别，超时才算真的验证过。

### 7_6 常见误区与进阶钩子

「1」误区：用 `json.Unmarshal` 处理超大或连续流。改用 `json.Decoder` 边读边解。
「2」误区：把 `http.Client` 零值当默认安全配置。必须显式设置超时，长任务用 `context` 控制。
「3」误区：用字符串拼接文件路径、手算时间差。用 `filepath.Join` 与 `time.Duration` 算术。
「4」误区：忽略 `Scanner` 的 `Err()` 与 token 过长限制。逐行处理时检查错误，必要时调大缓冲。
「5」误区：用拼接字符串写日志，或让中间件链靠全局变量传请求标识。改用结构化日志（标准库的 `slog` 按字段输出），把请求标识经 `context` 逐层下传；中间件本身也是一个 `http.Handler` 包一层 `http.Handler`，每层只加一件事。
「6」误区：在 `json` 标签里混用大小写与下划线，或忽略时间字段的序列化格式约定。对外契约先写字段表，再决定标签与自定义 `Marshaler`。
「7」进阶钩子：自己实现一个只含 `Read` 方法的小类型，把它接进 `io.Copy` 与 `bufio.Scanner`，验证无需改标准库一行代码就能复用整条管道，把过程记成接口契约卡。
