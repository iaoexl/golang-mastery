## 板块12 · 生产交付：反模式清单与通关总验收

### 12_1 核心机理与关键概念

前面十一个板块各自交付一种能力，板块12 把它们合成一次"能被别人接手"的交付。判断标准不是"我机器上跑通了"，而是"另一个人在干净环境里，按一份清单，能重建、能验证、能回滚"。

一次完整交付包含五层：可复现构建（锁定依赖、去掉本机路径、注入版本）、配置与密钥（外部注入、示例与真实分离）、可观测性（结构化日志、指标、请求标识）、安全网（门禁全绿、故障演练清单、回滚步骤）、知识归档（所有场景卡可检索、例外有理由）。这五层缺一层，交付就依赖某个人的记忆。

同样重要的是把全册笔记收口。前面各板块留下了不同形态的记录：资料取用卡、环境快照卡、假设—反例卡、内存草图、接口契约卡、退出条件表、依赖决策卡、字段契约表、断言意图卡、性能基线表、故障演练清单、红线登记表。它们不该散在各处，而应汇成一个可按场景检索的卡片库，并配一份索引。

```text
  可复现构建   配置与密钥   可观测性   安全网   知识归档
      |            |           |          |          |
      +------------+-----------+----------+----------+
                           v
                 干净环境按清单重建
                           v
              门禁全绿 + 故障演练通过 + 可回滚
                           v
                     才叫"交付完成"
```

#### 可回滚性：降级不等于回滚

交付五层里写了"能回滚"，但不少团队把两件事混成一件：**降级**是依赖坏了仍给一个可解释的响应，**回滚**是把正在运行的代码换回上一版。前者保护单次请求，后者保护整个版本，判据互不通用。

| 维度 | 降级 | 回滚 |
| --- | --- | --- |
| 触发条件 | 下游超时、返回异常、限流 | 新版本上线后探针或门禁不达标 |
| 作用范围 | 一次请求或一段时间窗 | 整个运行版本 |
| 状态要求 | 允许返回带时间戳的旧结果 | 必须能读回新版本已写入的数据 |
| 结束方式 | 依赖恢复后自动收敛 | 显式切换指针并复跑门禁 |
| 验收判据 | 响应可解释、不静默给空 | 探针恢复、幂等重放结果一致 |

要让回滚真的能演，产物先得满足四条判据：

| 判据 | 含义 | 破坏它的做法 |
| --- | --- | --- |
| 版本可辨识 | 构建参数由产物元数据读出，注入版本串由启动日志字段验证 | 所有构建都叫同一个名字，或只靠"上次构建过"推断 |
| 配置外置 | 切换版本不需要改配置内容 | 把版本相关配置编译进产物 |
| 状态兼容 | 旧版本能读回新版本写过的数据 | 只做向前兼容、不做向后兼容 |
| 切换原子 | 保留上一版副本，切换失败可立刻指回 | 就地覆盖产物，没有可回退副本 |

四条里最常漏的是第三条。只验"服务能起来"、不验"新版本写过的请求在旧版本上重放结果一致"，等于只演了半程。12_5 因此要求"服务恢复"与"数据无损"同时成立，实战工程的 `scripts/rollback_drill.sh` 把这两项落成可重跑的命令。

实测校准：`go version -m` 会列出模块路径、构建参数与工具链信息，但不回显 `-ldflags "-X ..."` 注入的内容。所以"版本可辨识"要拆成两条判据：构建参数看产物元数据，注入版本看启动日志里的字段。

把两者合并成一句"内嵌版本与构建参数一致"，实测时就会拿不到后者的证据。回滚演练脚本正是按这个拆分来验的。

### 12_2 可落地操作清单

第1步：整理一份交付清单，逐项写明命令、预期输出、判定人，不写"检查一遍"这种模糊项。
第2步：在干净环境里只凭清单重建构建与测试，全程不复用本机缓存与容器层缓存，并清点存量构建环境的工具链支持状态，把每一步输出贴进交付记录。
第3步：核对配置与密钥：真实值不在版本库，样例文件可独立启动，缺项时程序给出明确报错。
第4步：跑一遍故障演练清单，逐条打勾，未演练过的边界补一个注入用例。
第5步：跑回滚演练脚本实演一次：从新版本切回上一版，同时验探针恢复与同一幂等键重放结果一致。构建参数看产物元数据、注入版本看启动日志字段，两类证据分开留痕；线上多实例流量切换另按 0_2 边界声明处理。
第6步：把全册场景卡按"场景类型"归档，建一份索引，确保每张卡的六字段完整、判定不为空。

### 12_4 案例小故事：接手的人只拿到一个能跑的二进制

一次内部交接，原作者把二进制和一句"配置在服务器上"交出去就结束了。接手的人想改一个超时参数，翻遍仓库找不到配置来源；想复现构建，发现本地能编、CI 编不过；想回滚，没人知道上一版产物在哪。功能其实一直正常，但没人敢动它。

后来按五层补齐：清单里写死构建命令与版本注入方式；配置改成环境变量并配一份样例；日志统一带请求标识；门禁脚本与故障演练清单入库；所有场景卡汇成一份带索引的卡片库。

补完后再做一次演练——让一位完全没参与过开发的人只凭清单，在干净环境里重建、跑门禁、注入一次慢下游故障、执行回滚。全程没问过原作者一句。

那次演练的结论被写在笔记首页：交付的终点不是"程序能跑"，而是"程序不依赖某个人也能被改动"。板块0 里那条"能跑不等于可复现"，到这里终于闭环。

### 12_5 实用验证：命令、预期与判定

```bash
gofmt -l .
go vet ./...
go test -race -count=1 ./...
go test -bench=. -benchmem ./...
go mod tidy && go mod verify
go build -trimpath -ldflags "-X main.version=release" -o bin/app ./cmd/app
go version -m bin/app
```

预期：`gofmt -l .` 无输出；`vet`、`-race`、测试全绿；`tidy` 后版本库差异为空；`verify` 输出全部校验通过；构建参数可由产物元数据读出、注入版本串可由启动日志字段验证；干净环境按同一清单重建结果相同；故障演练清单逐项打勾；回滚演练后服务恢复且数据无损；抽查五张场景卡均能复现原结论。

判定：这是全册唯一一次"全项验收"，采用一票否决——上列任何一项不达标，整体记"未通过"，回到对应板块补完再重跑。全部达标后，在索引里把本次验收的命令、输出摘要与判定写成最后一张卡，命名"通关记录"。此后每次重大改动，只需重跑这份清单，不必重读全册。

"全项"必须落到能逐行打勾的载体上，否则一票否决只是句口号。下表随交付清单一并打印，"现场判定"列由执行人手写"通过 / 不通过 / 待查"，不预填、不事后补。

| 验收项 | 命令或动作 | 通过标准 | 现场判定 | 不达标回到 |
| --- | --- | --- | --- | --- |
| 格式 | `gofmt -l .` | 无输出 | 待填 | 1_2 |
| 静态检查 | `go vet ./...` | 退出码为 0 | 待填 | 1_5 |
| 竞态与测试 | `go test -race -count=1 ./...` | 全绿且零竞态告警 | 待填 | 8_5 |
| 基准数值 | `go test -bench=. -benchmem ./...` | 三列数值可复算 | 待填 | 9_5 |
| 依赖一致性 | `go mod tidy && go mod verify` | tidy 差异为空，verify 全部通过 | 待填 | 6_5 |
| 产物与元数据 | 带 `-trimpath` 与 `-ldflags` 构建；`go version -m` 读构建参数，启动日志读注入版本 | 两类证据分别可读，且与构建命令一致 | 待填 | 6_5 |
| 干净环境重建 | 空目录只拷源码与模块文件，不复用本机缓存重跑 | 输出与本机一致 | 待填 | 12_2 |
| 故障演练与回滚 | 跑 `scripts/rollback_drill.sh`：双版本切换、探针恢复、逐条重放比对 | 注入项全覆盖；探针恢复与幂等重放一致，输出演练通过标记 | 待填 | 12_2 |
| 卡片库抽查 | 任取五张场景卡复现原结论 | 六字段齐全、判定不为空 | 待填 | 12_3 |

九项全部写"通过"才允许把整体判定记为"通关"。任意一项写"不通过"或"待查"，按最后一列跳回对应小节，补完后再从本表第一行重跑一遍，不做局部补签。

环境适配不改判定口径：模块代理不可达时显式关闭代理并确认依赖全部来自本地，工具链位于自定义目录时先设好工具链根目录与 PATH，交叉编译则按目标组合逐个验。这些只改变"怎么把命令跑起来"，不改变"干净环境、同命令重跑、版本库差异为零"这三条通过标准。

"故障演练与回滚"一项不接受"移交部署侧"作为豁免：本地可用 `scripts/rollback_drill.sh` 演完整半程——构建两版产物、切到新版本写入请求、回退到旧版本、按记录逐条重放并比对。

线上多实例流量切换仍属部署侧，但"服务恢复"与"数据无损"这两条判据在本地就必须拿到实物证据。

### 12_6 常见误区与进阶钩子

「1」误区：把交付当成发版动作。它是"别人能接手"的能力，包含清单、演练与归档。
「2」误区：清单里写"检查配置""确认没问题"。每项必须带命令、预期、判定，能被机器或数值确认。
「3」误区：笔记只记成功结论。反例清单、此路不通清单、待查项才是复盘时最该先看的部分。
「4」误区：以为回滚步骤写完就够了。没演过的回滚等于没有回滚。
「5」误区：把降级当成回滚，或把版本串与构建参数合并成一条证据。降级护单次请求，回滚换整个版本；注入版本要另找启动日志或产物元数据之外的字段，两类证据分开留痕。
「6」全册反模式清单见下表。交付评审时逐行扫一遍，出现任意一条就回到"来源"列补完再重跑；这不是知识测验，是上线前的实物检查。

| 反模式 | 典型症状 | 根因 | 修正动作 | 来源 |
| --- | --- | --- | --- | --- |
| 起 goroutine 不写退出条件 | 协程数只涨不降，内存不回落 | 没有取消信号，也没有收敛点 | 每个协程在退出条件表里写"谁让它停"，用 `ctx.Done()` 与 `WaitGroup` 收口 | 5_3 |
| 错误只记日志不改控制流 | 日志里有报错，程序仍拿零值往下跑 | 把错误当成可观测事件而非分支 | 每个 error 当场决策：包装向上、就地处理或终止 | 2_1 |
| 返回子切片不注明共享 | 调用方改一处，别处数据跟着变 | 描述符共享同一底层数组 | 用完整切片表达式限 cap，或 `copy` 出独立副本并在契约里写明 | 3_1 |
| 实现方定义胖接口 | 换一个实现要连带改调用方 | 接口由实现方而非消费方定义 | 调用方定义最小接口，实现方不 import 消费方 | 4_1 |
| 外部调用不设超时 | 请求偶发堆积，重启就好 | 客户端零值不带超时 | 显式设置 `Timeout`，并用带 `context.WithTimeout` 的请求逐层下传 | 7_1 |
| 重试无退避无幂等 | 下游抖动升级成重试风暴，出现重复记录 | 立即重试，且写操作没有去重键 | 指数退避加抖动、次数与总耗时双上限、入口生成幂等键 | 10_1 |
| 用 `any` 替代约束 | 类型错推迟到运行时才炸 | 约束没把类型集合说窄 | 写自定义约束或 `comparable`，让实例化在编译期判定 | 4_1 |
| 手改 `go.sum` 或生成物 | 本地能编、CI 校验和不匹配 | 绕过工具链维护的一致性 | `go mod tidy` 与 `go mod verify`；生成物加醒目标记并在门禁比对差异 | 6_5 |
| 拿覆盖率百分比当质量 | 数字漂亮仍出线上事故 | 只说明被执行过，不说明被验证过 | 每条断言写"失败说明什么坏情形"，做红—绿对照 | 8_3 |
| 优化无前后数值 | 改了一堆，说不清到底快没快 | 缺同命令同环境的基线 | 先测量、单点改动、复测，数值归档进性能基线表 | 9_3 |
| 依赖检查塞进存活探针 | 下游一抖，全体实例被重启 | 存活与就绪职责混用 | 依赖检查放就绪探针，存活只判本进程是否卡死 | 10_1 |
| 业务层用 `reflect` 规避设计 | 字段类型一改，运行时悄悄生成错条件 | 类型错误被推到运行时 | 先问能否用接口或泛型；确需使用就附红线卡与基准数值 | 11_3 |
| 把降级当成回滚 | 依赖恢复后仍跑着坏版本 | 两者作用范围与结束方式不同 | 降级自动收敛，回滚显式切版本指针并复跑门禁，两条判据分开验 | 12_1 |
