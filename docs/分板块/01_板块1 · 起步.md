## 板块1 · 起步：工具链、模块与第一个可交付程序

### 1_1 核心机理与关键概念

Go 的起步成本之所以低，是因为它把"项目"这个概念压缩成一个模块声明加一个入口包。理解三件事即可展开全部工程实践：

第一，模块是依赖与版本的边界，由 `go.mod` 声明路径、工具链版本与依赖集合；`go.sum` 记录依赖内容的校验值，用于防篡改与可复现构建。第二，包是编译与可见性的边界，同一目录内只能有一个包名（测试包例外），首字母大写决定跨包可见。

第三，`main` 包加 `main` 函数才是可执行入口，其余包一律是库。

构建链路可以画成一条单向管道，任何一环卡住都会以明确的错误位置暴露出来，这正是它适合做"可验证学习"的原因。

```text
  .go 源码 -> 包解析 -> 类型检查 -> 编译 -> 链接 -> 可执行产物
                 |          |                        |
              import 路径  编译期错误在此拦截      go build -o
                 v
             go.mod / go.sum 解析依赖
```

起步阶段真正要记的不是命令全集，而是"每条命令改的是什么"。按改动对象分组，排障时就不会把环境问题和代码问题混在一起。

| 命令 | 改动对象 | 该看的输出 | 常见误判 |
| --- | --- | --- | --- |
| `go mod init` | 新建 `go.mod` | 模块路径 | 路径随手写，之后无法被正确引用 |
| `go mod tidy` | `go.mod` 与 `go.sum` | 增删差异 | 当成"格式化命令"，不看差异就提交 |
| `go mod download` | 本地模块缓存 | 下载了哪些模块 | 以为它等价于"装好了" |
| `go mod verify` | 只读校验 | 是否全部一致 | 与 `tidy` 混用，改坏文件还以为已修复 |
| `go run .` | 临时产物 | 程序输出 | 写成单文件参数，绕过模块解析 |
| `go build -o` | 可执行产物 | 文件是否生成且可执行 | 只验证"能编译"，不验证"能独立运行" |
| `go test ./...` | 无 | 每个包的结果 | 只跑当前目录，漏掉子包 |
| `gofmt -l .` | 只读检查 | 待格式化文件列表 | 以为加了 `-w` 才叫检查 |

几个环境变量决定"东西放在哪、从哪拿"，换机器时先打印它们，比反复重装有效：

| 变量 | 含义 | 异常时的症状 |
| --- | --- | --- |
| `GOMODCACHE` | 模块缓存目录 | 路径不可写或落在临时盘，容器里反复重下 |
| `GOPATH` | 默认工作区根 | 与模块模式混用，依赖解析行为不一致 |
| `GOPROXY` | 模块下载来源 | 取不到私有模块，或来源不一致导致校验差异 |
| `GOPRIVATE` | 不走公共代理的模块前缀 | 私有库被当成公共库请求，认证失败 |
| `GOOS` / `GOARCH` | 交叉编译目标 | 产物平台与运行环境不符 |

```text
  排障顺序: 先 go env 看落点 -> 再 go mod verify 看内容 -> 最后才改代码
       |              |                    |
    环境类          依赖类               代码类
  换机器先跑      不手改 go.sum      最小可复现片段
```

1_4 那个故事里的三个问题，本质上就是要求按这个顺序做归类。把"环境类 / 依赖类 / 代码类"写成场景卡的一栏，比记住十条命令更管用。

#### 从空目录到第一个文件：目录安排的决策依据

起步最容易漏的不是命令，而是"为什么这样放文件夹"。板块1 先用根目录单包跑通最小闭环，板块6 再演进到多入口布局；两阶段口径不同，但不是矛盾。

| 路径 | 解决什么 | 放错的后果 |
| --- | --- | --- |
| `go.mod` | 模块边界与依赖集合 | 退回旧工作区模式，导入路径无法解析 |
| `main.go`（起步） | 单包最小闭环 | 第一个文件还没跑通就先拆包 |
| `cmd/服务名`（板块6 起） | 多入口各自独立 | 入口与库混放，包名冲突 |
| `internal/包名` | 只被本模块内导入 | 外部依赖内部细节，改一处炸一片 |
| `scripts/` | 门禁、快照、演练脚本 | 命令散在个人笔记，换机器不可复跑 |
| `bin/`、`dist/`（不入库） | 本地产物与发布归档 | 二进制混进版本库 |

演进口径对齐：起步用 `go run .`；入口迁到 `cmd/服务名` 后改 `go run ./cmd/服务名`，README_5 硬门槛按后者写。脚本与产物目录从第一天就留好，后面只往里填文件，不必推倒重来。

**第一次打包发布**：板块1 就能做，不必等到板块12。`go build -trimpath -o dist/hello .` 产出独立文件，`go version -m` 读出模块路径与构建参数；把产物、元数据摘要与一份发布清单放进 `dist/`，并在版本库里排除该目录。

这一步的意义不是发版给别人，而是让"能跑"升级成"能交付"：接手的人拿到产物就能确认它从哪来、怎么重建。完整发布检查见 12_2，起步版实跑见 `scripts/bootstrap.sh`。

### 1_2 可落地操作清单

第1步：新建空目录并执行 `go mod init example.com/hello`，确认生成的 `go.mod` 中模块路径与预期一致。
第2步：写 `main.go`，包声明为 `package main`，入口函数里只做一次输出，先不引入任何依赖。
第3步：执行 `go run .` 验证能跑；再执行 `go build -o bin/hello .` 验证能产出独立文件。
第4步：执行 `gofmt -w .` 与 `go vet ./...`，把"格式化通过、静态检查通过"当作提交前的固定动作。
第5步：补一个 `main_test.go`，哪怕只断言一个纯函数返回值，也要让 `go test ./...` 出现 `PASS`。
第6步：执行一次 `go mod tidy`，观察 `go.mod` 与 `go.sum` 是否被意外改动，把差异记进场景卡。

第7步：按 1_1 的目录决策表核对当前文件落点，把 `bin/`、`dist/` 写进版本库排除清单，并确认 `scripts/` 已存下前面几条命令。
第8步：做一次最小打包发布，用 `go build -trimpath` 产出文件、`go version -m` 读构建参数，产物与发布清单一起放进 `dist/`。

这八步构成起步闭环：从空目录、第一个文件、文件夹安排，一直到第一次打包发布。后续所有板块都在这个闭环上叠加能力，而不是另起炉灶。

唯一会变的是入口位置：6_1 把 `main` 迁到 `cmd/服务名` 之后，`go run .` 要改写成 `go run ./cmd/服务名`，README_5 的硬门槛表也按同一口径同步，否则工具链会报 `no Go files`。

### 1_3 场景笔记法：环境搭建与首次构建

环境类笔记最容易写成"装好了"，一旦换机器就完全失效。用下面这张"环境快照卡"，关键是保留原始输出而不是结论。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明机器类型、容器镜像标识、新建目录路径 |
| 预期 | "go version 有输出；go build 产出 bin/hello；go test 出现 PASS" |
| 动作 | 逐行粘贴六条命令，不省略参数 |
| 观察 | 原样粘贴输出文本，包含版本串与警告，不要改写 |
| 判定 | 三项预期逐条标通过或不通过 |
| 迁移 | "下次新容器先跑这张卡，再写业务代码" |

实用补充：把六条命令存成项目根目录的 `scripts/baseline.sh`，每次换环境只跑脚本并比对输出差异。笔记里记录的是"差异"，不是重复的成功日志。

### 1_4 案例小故事：一个下午被 `go run` 吃掉

实习生小周接到的第一件事是"把统计脚本改成服务"。他照着旧笔记在共享目录里直接建了 `main.go`，敲 `go run main.go`，程序跑起来了，他便认为环境没问题。第二天换成容器构建，`go build ./...` 报出一串 import 找不到的错误。

带他复盘时只问了三个问题：有没有 `go.mod`？有没有用 `go run .` 而不是单文件？`go env GOMODCACHE` 指向哪里？三个答案全是"没看"。原来单文件模式绕过了模块解析，依赖全靠本机全局缓存，容器里自然全丢。

修法很朴素：补 `go mod init`、改用包级命令 `go run .`、把 `baseline.sh` 放进仓库。之后同样的代码在两台机器上输出完全一致。小周后来把这张场景卡贴在笔记首页，标题写的是"能跑不等于可复现"。这条结论一路支撑到板块6 的依赖锁定和板块12 的交付检查单。

### 1_5 实用验证：命令、预期与判定

```bash
go version
go mod init example.com/hello
go run .
go build -o bin/hello .
gofmt -l .
go vet ./...
go test ./...
go mod tidy
```

预期：`go run .` 输出程序里那行文本；`bin/hello` 文件存在且可直接执行；`gofmt -l .` 无输出；`go vet` 与 `go test` 退出码均为 0；`go mod tidy` 后版本库差异为空或有可解释的依赖增删。

判定：把 `echo $?` 接在每条命令后，记录退出码。全部为 0 且 `bin/hello` 可执行，记"通过"；任意一条非 0，先看错误首行属于"环境类"还是"代码类"，再决定是重跑基线卡还是改代码。

补一条强验证：把整个目录复制到另一个空目录再跑一次 `go test ./...`，结果一致才算真正可复现。

### 1_6 常见误区与进阶钩子

「1」误区：`go run main.go` 只编译单文件，同目录其他文件与模块依赖会被忽略。改用 `go run .` 或显式列出全部文件。
「2」误区：把项目放在旧式工作区目录里，依赖解析行为与模块模式不一致。用 `go env GO111MODULE` 确认。
「3」误区：手改 `go.sum`。它由工具链维护，出现校验冲突应回到 `go mod tidy` 与依赖来源排查。
「4」误区：格式化靠编辑器保存时自动完成，CI 里却没有校验。把 `gofmt -l .` 放进检查脚本。
「5」进阶钩子：执行 `go build -x .` 观察完整编译命令与缓存命中，尝试解释其中每一步在管道图上的位置，写进场景卡的"迁移"字段。
