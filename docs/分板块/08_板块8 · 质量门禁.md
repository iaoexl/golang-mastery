## 板块8 · 质量门禁：表驱动测试、基准、模糊测试与覆盖率

### 8_1 核心机理与关键概念

板块7 让功能跑通，板块8 让功能"敢改"。质量不是发布前的一次检查，而是每次改动都自动跑过的一组门禁。

Go 的 `testing` 包极简，靠表驱动把"输入—预期—断言"压成一张切片；子测试 `t.Run` 让每个用例独立命名、可单独重跑；`t.Helper` 让失败定位到调用行而不是工具函数内部。

基准测试 `BenchmarkXxx` 输出每次迭代耗时与分配次数，`-benchmem` 才能看到分配。模糊测试 `FuzzXxx` 由运行时自动生成输入，擅长抓解析类代码的边界崩溃。覆盖率 `go test -cover` 是"哪些行被跑到"，不是"哪些逻辑被证明"，两者不能混为一谈。

表驱动只是骨架，真正决定测试是否可靠的是 `testing` 提供的生命周期设施。它们大多不写在业务断言里，却直接决定"失败信息准不准、临时资源收不收得回、用例能不能并行跑"。

| 设施 | 解决的问题 | 用错的后果 |
| --- | --- | --- |
| `t.Helper()` | 把失败行号归因到调用方 | 报错全指向断言封装函数，排查要倒着翻栈 |
| `t.Cleanup()` | 无论成功失败都在用例末回收资源 | 失败分支提前返回，临时目录与连接泄漏 |
| `t.TempDir()` | 自动创建并随用例清理的隔离目录 | 多个用例共用固定路径，彼此踩踏 |
| `t.Setenv()` | 用例内临时改环境变量并自动还原 | 手工改全局环境，污染后续用例 |
| `t.Parallel()` | 声明用例可与其他并行用例同时跑 | 共享可变状态被并发改写，结果随调度漂移 |
| `t.Run()` | 子测试独立命名、可单独 `-run` 重跑 | 一批输入挤在一个函数里，失败无法定位到行 |
| `b.ResetTimer()` | 把构造输入的耗时排除在基准之外 | 准备成本混进 `ns/op`，数值不可比 |
| `b.ReportAllocs()` | 与 `-benchmem` 对齐输出分配次数 | 只盯耗时，漏掉分配速率上升 |

`Cleanup` 与 `defer` 的差别值得记牢：`defer` 在当前函数返回时执行，`t.Cleanup` 在整个子测试（含其所有并行分支）收敛后执行，且后进先出。并行用例里要用它，不要用 `defer` 抢跑。

假实现也要分层，不能"要么全真、要么全假"：纯函数用表驱动直接断言；涉及 HTTP 边界用 `httptest.NewServer` 起一个进程内伪服务，断言状态码、响应头与正文三件事；只有一层需要真实依赖时才连外部。三层各有职责，把全部依赖都 mock 掉，测到的其实只是自己写的假实现。

模糊测试与普通测试的区别在于语料会自己长大：`f.Add` 提供种子语料，运行时按覆盖反馈变异输入，崩溃后把能复现的最小输入写回语料目录。因此反例文件必须随代码一起提交，否则下次换机器跑同一条命令，那个崩溃就"消失"了。

覆盖率 `-covermode` 也有三种口径——`set` 只记是否执行，`count` 记执行次数，`atomic` 在并发下精确计数；做竞态检测时要用 `atomic`，只看行覆盖则用 `set` 更省。

门禁应该分层：格式化与 `go vet` 是秒级第一层；单元测试与 `-race` 是第二层；基准回归与模糊测试是第三层。把三层串成一条流水线，任何一层变红都不允许合并。再加一道容易被漏掉的门禁：`-shuffle=on` 随机执行顺序，专门抓"用例之间靠共享状态隐式耦合"。

```text
  测试用例启动
       |
       v
  t.TempDir / t.Setenv -> 登记 t.Cleanup(后进先出)
       |
       v
  t.Run 子测试 -> 采集断言结果 / 失败行号由 t.Helper 归位
       |
       v
  全部子测试收敛 -> 统一执行 Cleanup -> 释放目录与连接
```

```text
  改动提交
     |
     v
  第1层 gofmt -l / go vet       秒级，挡格式与可疑写法
     |
     v
  第2层 go test -race ./...     挡逻辑回归与数据竞争
     |
     v
  第3层 -bench -benchmem / fuzz 挡性能回退与边界崩溃
     |
     v
  覆盖率报告 -> 只看薄弱模块，不拿百分比当 KPI
```

### 8_2 可落地操作清单

第1步：把板块2 的解析函数改成表驱动测试，至少覆盖合法、空串、非数字、超范围四类，用 `t.Run` 命名。
第2步：封装一个断言小函数并加 `t.Helper`，故意让一个用例失败，确认报错行指向调用处。
第3步：用 `httptest` 测板块7 的处理器，断言状态码、响应头与正文三件事。
第4步：为热点函数写一个基准测试，执行 `go test -bench=. -benchmem`，记录 `ns/op` 与 `B/op`。
第5步：为解析函数写一个模糊测试，用 `f.Add` 放三条种子语料，跑一轮后确认反例文件被写进语料目录并随代码提交。
第6步：把门禁命令写进 `scripts/check.sh`，额外加一条 `go test -shuffle=on -count=1 ./...`，把固定顺序下看不出的状态耦合挡在合并之前。

### 8_3 场景笔记法：测试用例与失败复盘

测试类笔记的关键不是"通过率"，而是"这条断言在守什么"。用断言意图卡记录。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明被测函数、本次改动、想防住的回归 |
| 预期 | "新增用例在旧代码上变红、在新代码上变绿" |
| 动作 | 贴出表驱动用例行与断言行 |
| 观察 | 粘贴 `-v` 输出、失败时的期望值与实际值、基准数值 |
| 判定 | 能主动让旧代码失败记"通过"；只是跑绿了记"待查" |
| 迁移 | "每个修复 bug 的提交必须附带一条能复现该 bug 的用例" |

实用补充：建一份"红—绿对照表"，左列写"删掉哪行代码会让哪条用例变红"。复习时按左列抽查，比重新跑一遍全套测试更能发现假断言。

### 8_4 案例小故事：全绿的覆盖率，挡不住一次空指针

某模块覆盖率数字很漂亮，评审时大家都放心。上线后一个从未出现过的输入组合触发了空指针：解析函数对"字段存在但值为 null"的情况返回了一个零值结构体，调用方直接取了其中一个指针字段。

复盘发现测试表里全是"合法值"与"字段缺失"，唯独没有"字段存在但为 null"。补用例只花了十分钟，但真正改变的是笔记方式：此后每张断言意图卡必须先写一句"这条断言如果失败，说明什么坏情形发生了"，写不出这句话的用例不许进表。

团队还顺手做了两件事：给解析函数加模糊测试，让运行时帮忙找畸形输入；把覆盖率报告按包拆开看，专门盯数值最低的那两三个文件。数字不再当成绩，只当"哪里还没看过"的索引。这套做法后来延伸到板块9 的性能基线与板块12 的交付清单。

### 8_5 实用验证：命令、预期与判定

```bash
gofmt -l .
go vet ./...
go test -race -count=1 ./...
go test -shuffle=on -count=1 ./...
go test -bench=. -benchmem ./...
go test -fuzz=FuzzXxx -fuzztime=10s ./path/to/pkg
go test -covermode=atomic -coverprofile=cover.out ./... && go tool cover -func=cover.out
```

实测校准：`-fuzz` 只能指定单个包，不能跟 `./...`；多包写法会被工具链直接拒绝并提示 `cannot use -fuzz flag with multiple packages`。

把包名换成你要验证的那个包，其余命令仍可对整个模块跑。基准与模糊都建议指向被测包，避免把无关包的耗时混进数值。

预期：`gofmt -l .` 无输出；`vet` 与 `-race` 退出码为 0；`-shuffle=on` 与固定顺序两种跑法结果一致；基准输出含 `ns/op`、`B/op`、`allocs/op` 三列；

模糊测试在设定时长内不崩溃，或崩溃后生成可复现的反例文件；覆盖率报告能定位到未覆盖函数名。

判定：以"红—绿对照"为准——随机挑三条断言，分别删掉对应实现逻辑后重跑，三条都应变红。全部变红记"通过"；若某条删了实现仍全绿，说明它是假断言，先修断言再继续。模糊测试若发现崩溃，把反例固化为普通表驱动用例后重跑，直到全绿。

### 8_6 常见误区与进阶钩子

「1」误区：把覆盖率百分比当质量目标。它只说明被执行过，不说明被验证过。
「2」误区：测试里用 `time.Sleep` 等异步结果。改用 channel、`WaitGroup` 或带超时的 `select`。
「3」误区：基准测试忘记消费结果，被编译器优化掉。把结果赋给包级变量或做一次可观察使用。
「4」误区：表驱动用例只写合法输入。畸形、边界、并发三类必须各占一行。
「5」误区：给共享可变状态的用例加 `t.Parallel()`，或在并行用例里用 `defer` 做清理。改用 `t.Cleanup` 并让每个子测试持有自己的数据。
「6」误区：把模糊测试生成的反例文件排除在版本库之外，或只在本机跑过就算通过。反例必须随代码提交，换机器仍可复现。
「7」误区：把 `-covermode=set` 的结果当成并发安全统计，或只看总百分比。按包拆开看薄弱模块，竞态场景用 `atomic` 口径。
「8」进阶钩子：用 `go test -json ./...` 把一次门禁运行的事件流存成文件，统计最慢的三个测试，把优化前后耗时写进场景卡的"观察"字段。
