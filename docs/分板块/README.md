## README · 导览

### README_1 这套知识库解决什么

这是一套以"能力闭环"为轴心的语言精进手册。多数入门材料按语法点排队：变量、循环、函数、结构体……学完仍写不出一个能交付的东西。本册换了编排轴心——按"一个程序被写出来、被读懂内存、被抽象、被并发调度、被测试、被观测、被调优、被交付"的真实链路推进。

地基阶段建立可运行的最小闭环；内核阶段拆开类型、零值、内存布局与接口；并跑阶段进入 goroutine、channel 与 context；交付阶段落到模块、标准库、质量门禁；精进阶段处理性能、系统边界与生产收口。知识点只是骨架，能复现、能记录、能验收才是血肉。

因此自板块1 起，每个板块固定配齐三样可执行的东西：照着做就能出结果的操作清单、一套对应该场景的笔记记录方法、一组能当场判定成败的验证动作。读完不算学会，验证通过才算过关。

这套手册的"从入门到精通"不是宣传语：README_8 给出入门、进阶、精通三级刻度与晋级判据，0_1 把七阶段与三级对齐，板块1 用一条起步闭环把"空目录 → 第一个文件 → 文件夹安排 → 打包发布"跑成实物。取用顺序见仓库根目录 `README.md`。

### README_3 记号、图示与笔记约定

「1」全文序号统一用「1」「2」或"第1步"，不使用带圈序号，也不使用带括号的圆圈编号。
「2」所有图示均为 ASCII 字符画，放在 `text` 代码块内。语雀与 Typora 直接渲染，无外链、无防盗链、无需解码，离线也能看。
「3」板块0 为总纲四节；自板块1 起，每个板块固定六节：X_1 核心机理、X_2 可落地操作清单、X_3 场景笔记法、X_4 案例小故事、X_5 实用验证、X_6 常见误区与进阶钩子。
「4」笔记统一采用"场景卡"结构，六字段如下：

| 字段 | 记什么 | 反例 |
| --- | --- | --- |
| 场景 | 当时在做什么、输入是什么 | 只写"研究了切片" |
| 预期 | 动手前写下的可判定结果 | 事后补写"本来就该这样" |
| 动作 | 实际敲下的命令或改动的几行 | 只写"调整了一下" |
| 观察 | 原始输出、报错原文、耗时数值 | 写成"报错了，后来好了" |
| 判定 | 通过 / 不通过 / 待查，附依据 | 空着 |
| 迁移 | 下次哪个场景能复用这条结论 | 空着 |

「5」验证统一三段式：命令 → 预期 → 判定。判定必须能被机器或数值确认，不写"感觉快了"。

```text
  场景发生 -> 写下预期 -> 执行动作 -> 记录原始观察
      ^                                    |
      |                                    v
  迁移复用 <- 归档场景卡 <- 给出判定 <- 对照预期
```

### README_4 三十分钟起步

第1步：装好工具链，执行 `go version` 与 `go env GOMODCACHE`，把两行输出原样贴进第一张场景卡的"观察"字段。
第2步：建一个空目录，执行 `go mod init example.com/hello`，写一个只打印一行文本的 `main.go`，跑通 `go run .`。
第3步：为它补一个表驱动测试，执行 `go test -v ./...`，看到 `PASS` 后再翻到板块0。

这三步不是热身，而是后面全部板块的验证底座：任何阶段出问题，都先回到这个最小闭环，确认是知识问题还是环境问题。

按阶段各留一条最短门禁命令。它们不是全集，而是"只要这条不过，后面的都别跑"的硬门槛：

| 阶段 | 一条硬门槛命令 | 通过标志 |
| --- | --- | --- |
| 能跑 | `go run ./cmd/app && go vet ./...` | 入口按实际包路径替换；输出预期文本，无告警 |
| 懂内存 | `go test -race ./...` | 零竞态告警 |
| 会抽象 | 换掉实现后 `go build ./...` | 调用方一行未改仍编译通过 |
| 能并发 | `go test -race -shuffle=on -count=10 ./...` | 重复十轮无竞态、无泄漏，随机顺序结果一致 |
| 可交付 | 干净目录里 `go mod verify && go test ./...` | 校验和一致，测试全绿 |
| 能精进 | `go test -bench=. -benchmem ./...` | 三列数值可复算 |
| 收口 | 门禁脚本加回滚演练脚本 | 九项全通过，且探针恢复与幂等重放均有证据 |

三条检索纪律：

「1」第1步先按症状定位到机理小节，不要直接跳到命令块抄命令；命令脱离了判定口径就只剩形式。
「2」第2步同一现象在表里出现两处时（例如超时既在 7 也在 10），先查本层的接口契约，再查跨层的预算分配，由内向外排除。
「3」第3步每次反查结束都要落一张场景卡，把"我以为的原因"与"实际验证出的原因"并排写进"观察"字段；反例清单比索引本身更值钱。

### README_7 配套实战项目与逐项跑通映射

前六节回答"读什么、怎么查、概念在哪"，这一节回答"整套知识库能不能真的跑起来"。仓库根目录 `golang-mastery` 放一套可运行工程：目录按板块拆，机理落进真实文件，再用一条门禁脚本把 12_5 的九项判分表串成可重跑的命令。它不是示例片段，换台机器照着重跑，应当得到同样的判定。

| 阶段 | 对应板块 | 实战工程里的落点 | 一条验证命令 | 对应判分项 |
| --- | --- | --- | --- | --- |
| 能跑 | 板块1 | `go.mod`、`cmd/app/main.go`、`scripts/baseline.sh` | `go run ./cmd/app` | 格式、静态检查 |
| 懂内存 | 板块2、板块3 | `internal/core/parse.go`、`slice.go` | `go test -race ./internal/core` | 竞态与测试 |
| 会抽象 | 板块4 | `internal/core/store.go` | `go test -run TestStoreAndGenericSum ./internal/core` | 竞态与测试 |
| 能并发 | 板块5 | `internal/core/worker.go` | `go test -race -count=10 ./internal/core` | 竞态与测试 |
| 可交付 | 板块6、板块7 | `scripts/check.sh` 的 L4 | `go mod tidy && go mod verify && go build -trimpath` | 依赖一致性、产物元数据 |
| 能精进 | 板块8、板块9 | `internal/core/bench_test.go` | `go test -bench=. -benchmem ./internal/core` | 基准数值 |
| 收口 | 板块10 至板块12 | `cmd/app/main_test.go`、`scripts/check.sh` | `bash scripts/check.sh` | 全项一票否决 |

两条实测校准，来自把工程真正跑通时踩到的坑：

「1」第1步入口位置会变。板块1 的根目录单包阶段用 `go run .`；6_1 把入口迁到 `cmd/服务名` 之后，必须改成 `go run ./cmd/服务名`，否则工具链报 `no Go files`。README_5 的硬门槛表已按后者写。

「2」第2步模糊测试只能指定单个包。`go test -fuzz=FuzzXxx -fuzztime=10s ./...` 会被拒绝并提示 `cannot use -fuzz flag with multiple packages`，8_5 已改为指向被测包。基准同理，指向具体包才不会把无关包耗时混进数值。

「3」第3步版本串与构建参数要分开验。`go version -m` 不回显 `-ldflags "-X ..."` 注入的内容，它给出的是模块路径与 `-trimpath` 一类构建参数。

注入的版本串要看启动日志里的字段。12_1、12_5 与回滚演练脚本都已按这个拆分写，别把两类证据合并成一句"内嵌版本与构建参数一致"。

另外三条工程口径在实战里也得到验证：干净环境只拷源码与模块文件、不复用本机缓存，重跑结果一致；交叉编译分别选中对应构建标签；`go test -json` 的事件流能直接统计最慢用例。命令、输出摘要与逐项判定见仓库根目录 `跑通记录.md`。

跑通记录是对照模板，不是标准答案。每次换环境都要自己重跑、自己填"现场判定"列；把别人的"通过"抄进自己的清单，等于把 12_5 的一票否决架空。

### README_8 从入门到精通：三级能力刻度与晋级判据

前七节给的是"怎么查、怎么跑、怎么落地"，这一节回答"我现在算到哪一级、凭什么进下一级"。七阶段是能力闭环，三级是能力刻度，两者是同一条路的两把尺子，不是两套课程。

| 层级 | 对应板块 | 能力定义 | 晋级判据 | 典型卡点 |
| --- | --- | --- | --- | --- |
| 入门 | 板块1 至板块4 | 能从空目录建起第一个文件、跑通最小闭环、解释值与内存、写出可替换的小组件 | 换台机器照清单重建全绿，且能说清每个文件夹解决什么 | 命令抄全了，却说不清 `go.mod` 与包边界 |
| 进阶 | 板块5 至板块8 | 能写可取消的并发管道、按工程布局组织依赖、用标准库搭服务、让每次改动都过门禁 | 竞态、随机顺序、覆盖率三类门禁全绿；红—绿对照能主动让实现变红 | 单测全绿，一上并发就泄漏 |
| 精通 | 板块9 至板块12 | 能用剖析数值定位瓶颈、守住系统边界、给高级工具划红线、按清单交付并回滚 | 12_5 九项全通过；回滚演练有本地实物证据；接手的人只凭索引能定位判断依据 | 写得出高性能代码，交不出可复现的判据 |

板块0 是总纲，不计入三级，但每一级都允许随时回查。

三条晋级纪律：

「1」第1步晋级不看读了多少页，只看"上一级的产出物能不能成为下一级的输入"。阶段三写出的可替换组件，到阶段五要能换成真实存储实现；换不动就说明上一级没过关。

「2」第2步每级留一张晋级判定卡（12_3 第十二类），六字段照专用模板填；"判定"列只写"通过"或"不通过"，不写"大致掌握""感觉会了"。

「3」第3步允许横向回查。到了精通阶段遇到类型或内存问题，按 README_5 反查回入门机理，不因为"已经学过"就跳过复跑。

起步那一关单独按一条线验：空目录 → 第一个文件 → 文件夹安排 → 第一次跑通 → 打包发布。实战工程的 `scripts/bootstrap.sh` 把这条线做成可重跑的命令，输出 `BOOTSTRAP_PASSED` 才算入门起步闭环通过。

目录安排的决策依据见 1_1，最小发布动作见 1_2，整体交付物见仓库根目录 `README.md` 与 `跑通记录.md`。
