## 板块2 · 语言内核：类型、零值、控制流与错误即值

### 2_1 核心机理与关键概念

Go 的类型系统有两条容易被忽略但决定代码形状的规矩：每个类型都有零值，且零值必须可用；错误是普通值，不靠异常机制传递。

零值可用意味着声明一个变量不必立刻初始化就能参与逻辑：数值为 0、布尔为 false、字符串为空串、指针与接口与切片与 map 与 channel 为 nil。工程上的直接后果是 `sync.Mutex` 零值即可用、`bytes.Buffer` 零值即可写，构造函数在很多场景下是多余的。

但 map 与 slice 的 nil 有行为差异：nil slice 可 `append`、可 `len`，nil map 可读不可写。

错误即值意味着函数签名把失败显式暴露出来，调用方必须当场决策：向上包装、就地处理、还是终止。配套工具是 `errors.Is` 判断链上是否含目标错误、`errors.As` 取出具体错误类型、`fmt.Errorf` 加 `%w` 保留包装链。

```text
  调用方  <---- (value, error) ----  被调用方
     |                                  ^
     |  errors.Is / errors.As           |
     +--> 就地处理 / %w 向上包装 / 终止 --+
```

与"错误即值"配套、却最常被漏讲的是 `defer`、`panic`、`recover` 的职责边界。`defer` 把清理动作注册到当前函数返回前执行，多个注册项按后进先出兑现；参数在注册那一行就求值，不是执行时再取。

具名返回值会被 `defer` 里的赋值改写，这既能做返回值修正，也最容易写出别人读不懂的代码。`panic` 是"本层无法继续"的展开信号，沿调用栈逐层执行 `defer`；`recover` 只在 `defer` 函数体内直接调用才生效，把展开转成普通错误值。

| 机制 | 生效时机 | 典型用途 | 越界写法 |
| --- | --- | --- | --- |
| `defer` | 当前函数返回前，后进先出 | 关闭文件、解锁、释放句柄 | 在长循环里累积注册项，直到函数结束才集体释放 |
| `panic` | 本层无法继续，逐层展开 | 初始化期断言、不变量被破坏 | 当业务错误分支用，或跨包边界抛出 |
| `recover` | 仅在 `defer` 内直接调用有效 | 服务边界把崩溃转成可观测错误 | 在普通函数里调用，静默失效 |
| `errors.Join` | 一批操作需要一起报错 | 批量校验聚合全部失败项 | 只留第一个错误，丢掉其余诊断信息 |
| `fmt.Errorf` 加 `%w` | 单条错误向上传递 | 保留可 `errors.Is` 判定的包装链 | 混用 `%v`，链条在某一层断掉 |

```text
  func handle() (err error) {
      defer func() {
          if r := recover(); r != nil {
              err = fmt.Errorf("边界兜住: %v", r)
          }
      }()                     // 第 1 个注册，最后执行
      defer resource.Close()  // 第 2 个注册，先执行
      // ...业务逻辑
  }
```

把三者连起来看：包装链解决"一条错误带上下文"，`errors.Join` 解决"一批错误一起返回"，`recover` 解决"崩溃不越出服务边界"。它们共同决定错误在系统里能走多远、能被谁看见，而不是只决定某行怎么写。

### 2_2 可落地操作清单

第1步：新建一个 `zero.go`，为每种基础类型声明变量后直接打印 `%#v`，亲手确认零值表，而不是背表格。
第2步：写一个返回 `(int, error)` 的解析函数，对非法输入返回带上下文的错误，用 `%w` 包住一个包级哨兵错误。
第3步：在调用方分别用 `errors.Is` 与 `errors.As` 做两种判定，确认包装后仍能识别。
第4步：把 `if err != nil` 的早返回写法固定成模板，禁止把错误塞进日志后继续往下跑。
第5步：用 `switch` 无表达式形式替换一长串 `if else`，用 `for` 的三种形态各写一遍（三段式、条件式、`range`）。
第6步：执行 `gofmt` 与 `go vet`，特别关注 `vet` 对 `fmt.Errorf` 格式串与未使用变量的提示。

### 2_3 场景笔记法：语法实验与语义求证

语法类结论最容易"以为懂了"。用"假设—反例卡"记录，强制自己写出一个能推翻假设的输入。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | "求证 nil map 是否可写" / "求证 %w 包装后 errors.Is 是否仍成立" |
| 预期 | 动手前写下明确断言，例如"包装后仍能 Is 到哨兵错误" |
| 动作 | 贴出最小可运行片段，不超过 15 行 |
| 观察 | 贴原始输出或 panic 全文，包含堆栈首行 |
| 判定 | 断言成立写"证实"，不成立写"推翻"，并改写原假设 |
| 迁移 | "凡涉及 nil 容器，先写读与写两个用例" |

实用补充：把每条被推翻的假设单独抄到笔记末尾的"反例清单"，复习时只看这份清单，效率远高于重读语法章节。

### 2_4 案例小故事：被吞掉的那一行日志

某次批量导入任务上线后，报表少了三分之一数据，却没有任何告警。代码里确实写了 `if err != nil`，但分支体只有一行 `log.Println(err)`，函数随后继续用零值结果往下算。错误被"看见"了，却没有被"决策"。

复盘时把那一段改成三选一：能重试就重试并计数，不能重试就 `return fmt.Errorf("导入第 %d 行: %w", lineNo, err)`，彻底致命才终止。同时在出口用 `errors.Is` 区分"格式错误"与"存储不可用"，前者进死信队列，后者触发整体失败。

改完后同一个坏输入第一次跑就出现在死信列表里，报表缺口从"事后发现"变成"当场可见"。团队后来把这条写进评审清单：`if err != nil` 分支里出现日志但既不返回也不改变控制流，一律打回。这条规则在板块8 的质量门禁里被固化成静态检查项。

### 2_5 实用验证：命令、预期与判定

第1步：把下面这段保存为 `verify_parse.go`，执行 `go run verify_parse.go`。它只依赖标准库，无需先建模块即可编译运行。

```go
package main

import (
    "errors"
    "fmt"
    "strconv"
)

var bad = errors.New("bad input")

func parse(s string) (int, error) {
    n, err := strconv.Atoi(s)
    if err != nil {
        return 0, fmt.Errorf("parse %q: %w", s, bad)
    }
    return n, nil
}

func main() {
    for _, s := range []string{"42", "", "abc", "999999999999999999999"} {
        n, err := parse(s)
        fmt.Printf("input=%-22q value=%d 命中哨兵=%t err=%v\n", s, n, errors.Is(err, bad), err)
    }
}
```

第2步：在完整项目里把这段逻辑改写成表驱动测试后，执行下列门禁命令。

```bash
go test -run TestParse -v ./...
go vet ./...
```

预期：四行输出中，合法输入 `42` 的 `value` 为 42、`err` 为 `<nil>`、命中哨兵为 false；其余三类 `value` 为 0、`err` 非 nil、命中哨兵为 true。

把包装动词从 `%w` 改成 `%v` 后重跑，三类非法输入的命中哨兵应全部翻转为 false。

判定：写一个表驱动测试，覆盖合法、空串、非数字、超范围四类输入，对每类同时断言返回值与 `errors.Is` 结果。四项全绿记"通过"，并额外验证一次"把 `%w` 改成 `%v` 后测试变红"——能主动让测试失败，才说明这条断言真的在守东西。

### 2_6 常见误区与进阶钩子

「1」误区：认为 nil slice 与空 slice 完全等价。序列化结果可能不同，对外返回前按接口约定统一。
「2」误区：用字符串比较判断错误类型。改用哨兵错误与 `errors.Is`。
「3」误区：`%w` 与 `%v` 混用，导致错误链在某一层断掉。评审时把格式化动词列为检查项。
「4」误区：`switch` 里忘记 Go 不会自动贯穿，或误以为需要 `break`。用无表达式 `switch` 写条件分支更清晰。
「5」误区：在循环体内 `defer file.Close()`，句柄要等整个函数返回才释放，长循环会把描述符吃满。改成即时关闭，或把单次处理提成独立函数。
「6」误区：以为 `recover` 放在任意函数里都能兜住崩溃。它只在 `defer` 内直接调用有效；批量任务应把多个失败项用 `errors.Join` 聚合，而不是只 `return` 第一个。
「7」进阶钩子：读一遍 `errors` 包的 `Unwrap` 约定，自己实现一个带 `Unwrap() error` 的自定义错误类型，并用 `errors.As` 取出它，把过程记成一张假设—反例卡。
