## 板块3 · 复合类型与内存模型：数组、切片、映射、结构体与指针

### 3_1 核心机理与关键概念

板块2 解决"一个值怎么来"，板块3 解决"一批值怎么放"。分界线是：谁持有底层存储、谁只是描述符。

数组是值，长度属于类型的一部分，赋值与传参会整体复制。切片是描述符，三字段为"指向底层数组的指针、长度、容量"，赋值复制的是描述符而非数据。映射是哈希表描述符，内部桶数组由运行时管理，赋值同样是描述符共享。结构体是字段的连续布局，字段顺序影响内存占用与对齐。指针则让"共享"变成显式动作。

由此推出三类高频 bug 的共同根因：切片扩容后旧描述符仍指向旧数组、多个切片共享同一数组导致意外改写、map 在并发写时直接崩溃。把这三类画在同一张图上，比背十条规则管用。

```text
  s := make([]int, 3, 5)
  +--------- descriptor ---------+        +--- backing array ---+
  | ptr | len=3 | cap=5 |  ----->  | 0 | 0 | 0 | . | . |
  +------------------------------+        +--------------------+
  s2 := s[1:]   -> ptr 指向同一数组的第 1 格，len=2 cap=4
  append 未超 cap  -> 复用原数组，s 与 s2 互相看得见改动
  append 超过 cap  -> 分配新数组，s2 仍指向旧数组，二者分家
```

逃逸分析决定存储落在栈还是堆：`go build -gcflags=-m` 会打印每个变量的逃逸结论。判断口径不是"用了 new 就上堆"，而是"编译器能否证明该变量的生命周期不超过当前函数帧"。返回局部变量地址、把指针存进接口、闭包捕获后外逃，都会触发逃逸。

结构体占用不是"各字段字节数相加"。每个字段按自身对齐要求落在相应边界，编译器在字段之间插入填充，整块大小还要向上取整到最大对齐值。把小字段聚拢到大字段之后，常常能在不改一行逻辑的前提下压缩占用。定位填充靠三件套，不靠目测：

| 观察项 | 取值含义 | 常见误判 |
| --- | --- | --- |
| `unsafe.Sizeof(v)` | 类型占用字节数，含尾部填充 | 当成"字段之和"，忽略尾部补齐 |
| `unsafe.Alignof(v)` | 该类型的对齐边界 | 以为所有字段都按 1 字节连续排布 |
| `unsafe.Offsetof(s.f)` | 字段相对结构体起点的偏移 | 只看声明顺序，漏掉字段之间的填充 |

```text
  未重排  { int8, int64, int8 }
    偏移: 0      8      16        Sizeof = 24
          (中间填充 7 字节 + 尾部填充 7 字节)
  重排后  { int64, int8, int8 }
    偏移: 0      8      9         Sizeof = 16
          (仅尾部填充 6 字节)
  判定口径: Sizeof / Alignof / Offsetof 三者都打印，不以推测为准
```

对象被推上堆之后，回收交给运行时的并发三色标记：对象初始为白色，从根集合出发把可达对象逐级标灰、再标黑，最终未被标到的白色对象即为垃圾。标记期间业务代码仍在改指针，因此要靠写屏障记录"黑色对象新指向白色对象"这类变动，避免漏标；整个回收只在少数阶段需要极短的暂停，即常说的 STW。

理解这条链路，才能解释板块9 里 `GODEBUG=gctrace=1` 打印的堆变化与暂停时长，也才明白"降低分配速率"为什么比"一味调大 `GOGC`"更根本。

### 3_2 可落地操作清单

第1步：写一个函数，对同一切片分别做"未超 cap 的 append"与"超 cap 的 append"，打印两次前后底层数组首元素地址与内容，把差异画成草图。
第2步：制造一次别名改写：从原切片切出子切片，修改子切片元素，再打印原切片，确认二者共享。
第3步：用 `copy` 与完整切片表达式 `s[low:high:max]` 各写一份隔离版本，体会"限制 cap 即限制共享范围"。
第4步：对结构体按字段顺序调整一次布局（把大字段放前、小字段聚拢），用 `unsafe.Sizeof` 打印前后字节数，理解对齐填充。
第5步：对 nil map 分别做读、写、`len`、`delete`，把四种结果写进反例卡。
第6步：执行 `go build -gcflags=-m ./...`，挑三个变量解释它们为何逃逸或不逃逸。

### 3_3 场景笔记法：内存推理与别名追踪

内存类问题看不到就记不住，所以笔记必须以"草图 + 地址"为证据，不能以"我懂了"为结论。这类笔记在卡片库里归入"假设—反例卡"的内存版：先用草图写下假设的地址与内容，再用实际输出推翻或证实它。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明切片长度、容量、原始内容，以及触发动作是 append 还是 reslice |
| 预期 | 动手前画出两张草图：动作前的描述符与数组、动作后的描述符与数组 |
| 动作 | 贴出打印地址与内容的最小片段 |
| 观察 | 粘贴实际地址与元素值，地址用十六进制原样保留 |
| 判定 | 草图与观察一致写"证实"，不一致标出具体哪一格判断错了 |
| 迁移 | "任何返回子切片的 API 都要在注释里写明是否共享底层数组" |

实用补充：给每个内存实验配一条"破坏性验证"——故意把 `cap` 调小或调大再跑一次，看结论是否翻转。能翻转的结论才是真规律，不能翻转的多半是巧合。

### 3_4 案例小故事：分页接口里悄悄变掉的第一条

某后台列表接口偶发首条数据被改，日志里找不到任何写库记录。排查到凌晨，最后发现问题在一个工具函数：它接收一批记录，返回 `records[:0]` 作为"清空后的容器"，调用方随后 `append` 进筛选结果。

因为容量足够，append 直接复用了原底层数组，把原始数据第 0 格覆盖掉了，而原始数据还被另一处缓存引用着。

修复没有加任何锁，只改了一行：用 `make([]Record, 0, len(records))` 新建独立底层数组，或者用完整切片表达式把 cap 锁死。补的测试也极朴素——调用工具函数后断言原切片内容不变。

复盘会上定下一条口径：函数签名里出现切片返回时，必须在注释里回答"共享还是复制"。这条口径后来被写进 4_3 的接口契约卡与 12_6 的反模式清单。别名 bug 的可怕之处从来不是难修，而是它不报错。

### 3_5 实用验证：命令、预期与判定

第1步：把下面这段保存为 `verify_slice.go`，执行 `go run verify_slice.go`。三行打印分别对应共享、扩容分家、未扩容仍共享。

```go
package main

import "fmt"

func main() {
    base := []int{1, 2, 3, 4, 5}
    sub := base[1:3]
    sub[0] = 99
    fmt.Println("共享底层数组:", base)

    grown := append(base, 6) // cap 已用尽，触发扩容
    grown[0] = 7
    fmt.Println("扩容后分家:", base, grown)

    roomy := make([]int, 3, 8)
    copy(roomy, []int{1, 2, 3})
    same := append(roomy, 4) // 未超 cap，复用同一底层数组
    same[0] = 7
    fmt.Println("未扩容仍共享:", roomy, same)
}
```

第2步：在完整项目里执行下列门禁命令。

```bash
go test -race ./...
go build -gcflags=-m ./... 2>&1 | grep -E "escapes|does not escape"
```

预期：第一行输出 `[1 99 3 4 5]`，说明子切片改动被原切片看见；第二行 `base` 仍是 `[1 99 3 4 5]` 而 `grown` 为 `[7 99 3 4 5 6]`，说明扩容后二者分家；

第三行 `roomy` 为 `[7 2 3]`、`same` 为 `[7 2 3 4]`，说明未扩容时改动互相可见。`-race` 退出码为 0；逃逸输出中至少能找到一条与闭包或接口相关的 `escapes to heap`。

判定：把三行打印逐条与预期对照，全中记"通过"。第三行本身就是破坏性验证——把 cap 预留得足够大后，同样的 `append` 不再分家；能看到这个翻转，说明掌握的是扩容规则，而非记住了某次输出。

### 3_6 常见误区与进阶钩子

「1」误区：把 `len` 当 `cap` 用，以为 append 一定分配新数组。用 `s[low:high:max]` 显式限容。
「2」误区：认为 `copy` 会扩容目标切片。它只复制到 `min(len(dst), len(src))` 为止。
「3」误区：对 nil map 赋值。先 `make`；但 nil map 读与 `delete` 是安全的，别一刀切加初始化。
「4」误区：把结构体字段顺序随意排列导致填充浪费。按字段大小聚拢，用 `unsafe.Sizeof` 量化。
「5」进阶钩子：写一个带指针接收者的方法，用 `-gcflags=-m` 观察接收者逃逸；再改成值接收者对比，把两次输出并排贴进场景卡。
