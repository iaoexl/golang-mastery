## 板块5 · 并发模型：goroutine、channel、select 与 context

### 5_1 核心机理与关键概念

板块4 让代码可替换，板块5 让代码同时跑起来。Go 并发的四块积木各有明确职责，混用就会出事。

goroutine 是轻量执行单元，由运行时调度到少量系统线程上，创建成本极低，但"极低成本"不等于"没有成本"：没有退出路径的 goroutine 就是泄漏。channel 既是数据管道也是同步点，无缓冲 channel 要求收发双方同时就绪，缓冲 channel 只解耦瞬时速率差。

关闭规则必须记牢：由发送方关闭，接收方永不关闭；向已关闭的 channel 发送会 panic，从已关闭的 channel 接收会先取尽剩余值再得到零值。`select` 处理多路就绪，配合 `default` 做非阻塞探测，配合 `context.Done()` 做取消。

context 是取消信号的传播树，不是数据仓库：只放跨调用链的请求范围值，且用自定义 key 类型避免碰撞。

`sync.WaitGroup` 管"等一批活干完"，`sync.Mutex` 管"一小段临界区"，`sync.Once` 管"只做一次"。把它们画成一条有始有终的管道，比记 API 列表更重要。

```text
   ctx, cancel := context.WithTimeout(parent, d)
        |
        v
  +----------+   jobs   +----------+   out   +----------+
  | producer | -------> | workers  | ------> | collector|
  +----------+  close   +----+-----+  close  +----+-----+
       |                     |                    |
       +-- 出错/超时 --> cancel() --------------> Done 被唤醒
                            |
                            v
                       WaitGroup.Wait -> 全部退出 -> 返回
```

"调度到少量系统线程上"具体是 GMP 模型：G 是 goroutine，M 是系统线程，P 是逻辑处理器并持有本地运行队列。P 的数量决定同一时刻能并行执行用户代码的 G 上限；

M 因系统调用阻塞时会与 P 解绑，P 转而去带另一个 M 继续跑，这正是 I/O 密集任务不会把整个进程拖死的原因。理解这一层，才明白"起了很多 goroutine"并不等于并行计算，也才读得懂 `runtime/trace` 里的调度延迟。

```text
   P (逻辑处理器, 持有本地队列)
      | 绑定
      v
   M (系统线程) --执行--> G1 G2 G3 ...
      |
   M 陷入阻塞系统调用 -> 与 P 解绑 -> P 另找空闲 M 继续跑队列
```

原语选型比记 API 列表更重要。同一份共享状态，用错原语通常会表现为"结果正确但吞吐塌了"或"偶发不一致"：

| 原语 | 解决的问题 | 不该用它做的事 |
| --- | --- | --- |
| `sync.Mutex` | 保护一小段临界区 | 包住整个 I/O 调用，把并发退化成串行 |
| `sync/atomic` | 单个数值的无锁读写 | 维护多个需要保持一致性的字段 |
| `sync.Map` | 读多写少、键集合稳定的并发映射 | 写密集或需要一致遍历快照的场景 |
| `sync.WaitGroup` | 等一批任务收敛 | 传递取消信号或错误信息 |
| `sync.Once` | 一次性初始化 | 需要按失败结果重试的初始化 |
| `errgroup` 风格任务组（扩展包） | 一组任务共享取消并聚合首个错误 | 每批需独立生命周期的长驻服务 |
| `singleflight` 风格单次合并（扩展包） | 抑制同一键的并发重复计算 | 跨请求长期缓存 |

`context.Value` 是最容易被滥用的一格。它只适合放真正跨调用链、且与请求同生命周期的元数据（请求标识、追踪上下文），不适合塞配置、连接池或可选参数。key 必须自定义非导出类型，避免不同包用字符串撞键；取值方要处理"键不存在"，不能假定上游一定放过。

判断标准很朴素：去掉这个 value，函数能不能用显式参数表达清楚？能，就不该放进 context。

### 5_2 可落地操作清单

第1步：写一个生产者—多 worker—收集者管道，明确谁关闭 jobs、谁关闭 out，把关闭点标在草图上。
第2步：给管道加一个 `context.WithTimeout`，故意让某个 worker 卡住，验证超时后所有 goroutine 都能退出。
第3步：用 `select` 同时监听 `ctx.Done()` 与结果 channel，确认取消分支能打断阻塞接收。
第4步：用 `runtime.NumGoroutine()` 在压测前后各打一次点，把差值作为泄漏判据写进笔记。
第5步：把一段共享计数改用 `sync.Mutex` 与 `atomic` 各实现一遍，用 `go test -race` 对比。
第6步：执行 `go test -race -count=10 ./...`，让竞态检测在重复运行中暴露偶发问题。

### 5_3 场景笔记法：并发排障与泄漏取证

并发 bug 不会稳定复现，笔记必须记录"证据链"而不是"印象"。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明 goroutine 数量、channel 缓冲大小、超时时长、触发的输入 |
| 预期 | "取消后 NumGoroutine 回到基线（与启动前相等或相差不超过 1）；-race 零告警；无 panic" |
| 动作 | 贴出超时设置、cancel 调用位置、Wait 位置三处关键代码 |
| 观察 | 粘贴 race 报告全文（若有）、前后 goroutine 数、退出耗时 |
| 判定 | 三项数值同时达标记"通过"，任一不达标写"待查"并保留现场 |
| 迁移 | "凡起 goroutine 先写下它的退出条件，写不出就别起" |

实用补充：给每个并发组件建一张"退出条件表"，逐行列出每个 goroutine 由谁、在什么信号下退出。评审时只看这张表，能发现八成泄漏。

### 5_4 案例小故事：半夜涨到上万的 goroutine

一个聚合服务在流量高峰后内存不回落，监控上 goroutine 曲线像台阶一样只涨不降。代码看着很规整：每个请求起若干 goroutine 去拉下游，结果写进一个无缓冲 channel，主协程取够三条就返回。

问题恰恰在"取够就返回"——剩下的 goroutine 还在往那个没人收的 channel 上发送，永远阻塞。

修法是两步：用 `context.WithTimeout` 给整批请求一个统一截止；结果 channel 改成有足够缓冲或由收集者保证取尽，并让每个 worker 在 `select` 里同时监听 `ctx.Done()`。

补的验证也很直接：压测前后打印 `runtime.NumGoroutine()`，差值必须回到基线附近。

上线后再跑同一波流量，曲线变成尖峰后立刻落回。复盘时大家公认最值钱的不是那几行代码，而是新加的一张"退出条件表"：每个 goroutine 都得回答"谁让我停"。这张表后来成了 12_6 反模式清单的第一条。

### 5_5 实用验证：命令、预期与判定

第1步：把下面这段保存为 `verify_cancel.go`，执行 `go run verify_cancel.go`。`slow` 是一个永不写入的通道，用来模拟卡住的下游。

```go
package main

import (
    "context"
    "fmt"
    "runtime"
    "time"
)

func main() {
    base := runtime.NumGoroutine()
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()

    slow := make(chan int) // 永不写入，模拟卡住的下游
    out := make(chan int, 4)
    for i := 0; i < 4; i++ {
        go func() {
            select {
            case <-ctx.Done():
                return
            case v := <-slow:
                out <- v
            }
        }()
    }

    select {
    case v := <-out:
        fmt.Println("收到结果:", v)
    case <-ctx.Done():
        fmt.Println("超时退出:", ctx.Err())
    }

    time.Sleep(50 * time.Millisecond) // 给退出留出可观察窗口
    fmt.Println("goroutine 基线/当前:", base, runtime.NumGoroutine())
}
```

第2步：在完整项目里执行下列门禁命令。

```bash
go test -race -count=10 ./...
go test -run TestPipeline -v ./...
```

预期：程序打印 `超时退出: context deadline exceeded`，末行两个数字相等或相差不超过 1；`-race -count=10` 全程零告警。

把 worker 的 `select` 里 `ctx.Done()` 分支删掉后，四个 worker 会一直卡在 `slow` 上，末行第二个数字明显高于基线。向已关闭 channel 发送的破坏性用例应稳定 panic 而非静默。

判定：三项同时满足记"通过"。删掉 `ctx.Done()` 分支后能看到 goroutine 数上升，就是取消链路生效的反向对照；只看一次正常跑完不算验证。

### 5_6 常见误区与进阶钩子

「1」误区：接收方关闭 channel，或由多个发送方各自关闭同一个 channel。统一由唯一发送方在所有发送完成后关闭。
「2」误区：把 context 当可选参数到处传 `context.Background()`。请求入口创建一次，逐层向下传。
「3」误区：用 `time.Sleep` 等 goroutine 完成。改用 `WaitGroup` 或带 `Done()` 的 `select`。
「4」误区：以为 `-race` 跑一次通过就安全。竞态需要重复运行与并发压测才有机会暴露。
「5」进阶钩子：用 `runtime/pprof` 抓一次 goroutine profile，数出阻塞在 channel 发送上的栈数量，与 `NumGoroutine` 差值对照，把两份证据并排贴进场景卡。
