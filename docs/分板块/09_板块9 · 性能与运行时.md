## 板块9 · 性能与运行时：逃逸分析、剖析与分配优化

### 9_1 核心机理与关键概念

板块8 保证"改不错"，板块9 保证"改得快且快得有证据"。性能工作最容易走偏的地方，是凭直觉优化一个根本不热的路径。

正确顺序永远是三段式：先测量、再定位、后改动、再测量。测量用基准测试给出 `ns/op`、`B/op`、`allocs/op` 三个基线值；定位用 `pprof` 看 CPU 火焰图与堆分配来源，用 `-gcflags=-m` 看逃逸，用 `runtime/trace` 看调度与阻塞；

改动只针对定位出的那一处。GC 侧关注分配速率而非总内存：`GOGC` 调的是"相对上一次存活堆增长多少触发回收"，`GODEBUG=gctrace=1` 能直接打印每次回收的耗时与堆变化。

常见有效手段就那么几类：预分配切片容量减少扩容拷贝、用 `strings.Builder` 或 `bytes.Buffer` 替代循环字符串拼接、用 `sync.Pool` 复用短生命周期大对象、把不必要上堆的指针改回值传递。每一类都必须拿改动前的基线来对照，否则就是自我感觉。

```text
  基线测量 -> 剖析定位 -> 单点改动 -> 复测对照 -> 归档数值
     |           |           |           |           |
  -benchmem   cpu/heap   只动一处    同样命令    场景卡留存
              -gcflags                 同环境
                 v
       改善不成立 -> 回退改动，保留"此路不通"的笔记
```

pprof 的几类 profile 回答的是不同问题，混用会得出方向相反的结论。CPU profile 按采样统计"谁在占用 CPU 时间"；堆 profile 按分配点统计"谁在制造对象"；阻塞与互斥 profile 看"谁在等"；

goroutine profile 看"谁还活着、卡在哪一行"。堆 profile 又有两种常用视图：`alloc_space` 是累计分配字节（含已回收），`inuse_space` 是当前仍存活的字节。前者定位分配热点，后者定位内存驻留；

只盯一个，容易把"分配很快但立刻回收"误判成泄漏，也可能漏掉高频短命对象带来的 GC 压力。

| 视图 | 回答的问题 | 常见误读 |
| --- | --- | --- |
| CPU profile | 哪些函数占用 CPU 时间 | 把等待 I/O 的低 CPU 函数当成"不热" |
| `alloc_space` | 累计分配发生在哪 | 与驻留内存混为一谈 |
| `inuse_space` | 当前存活对象占多少 | 忽略高频短命分配造成的 GC 压力 |
| block / mutex profile | 阻塞与锁竞争在哪 | 只看 CPU 就完全看不到这类瓶颈 |
| goroutine profile | 还有哪些协程、卡在哪一行 | 与分配量混淆，误判泄漏来源 |

基准数字同样要按统计口径读。`-benchtime` 决定单轮测量时长，太短会被计时噪声淹没；`-count` 决定重复轮数，单轮结果不足以判定改善；`ns/op` 必须与 `B/op`、`allocs/op` 一起看，因为耗时下降而分配上升，往往只是把成本从函数体挪给了 GC。

基准函数里要真正消费计算结果，否则编译器可能把整段逻辑优化掉，得到一条漂亮但为空的基线。

### 9_2 可落地操作清单

第1步：为热点函数建一张基线表，固定记录输入规模、机器标识、`ns/op`、`B/op`、`allocs/op` 四项。
第2步：执行 `go test -bench=. -benchmem -cpuprofile=cpu.out`，用 `go tool pprof -top cpu.out` 找出前三个热点函数。
第3步：用 `go test -memprofile=mem.out`，再用 `go tool pprof -alloc_space mem.out` 定位分配来源。
第4步：执行 `go build -gcflags=-m ./...`，挑出热路径上的逃逸变量，逐个判断能否改回栈上。
第5步：只做一处改动（例如预分配容量），用完全相同的命令与环境复测，算出改善百分比。
第6步：用 `GODEBUG=gctrace=1` 跑一次真实负载，记录 GC 频率与单次暂停量级，写进场景卡。

### 9_3 场景笔记法：性能基线与改动对照

性能结论必须可复算，所以笔记里"环境条件"与"数值"同等重要。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明负载规模、并发数、机器与工具链标识、是否关闭其他负载 |
| 预期 | 动手前写"改动后 B/op 下降且 ns/op 不劣化"，不写"应该更快" |
| 动作 | 贴出改动前后的两行代码 diff 与完全相同的基准命令 |
| 观察 | 粘贴两轮完整基准输出与 pprof 前三项，保留原始数值 |
| 判定 | 三轮重复测量趋势一致记"通过"；波动大于改善幅度记"待查" |
| 迁移 | "任何优化提交必须附前后数值；无数值不合并" |

实用补充：单独维护一份"此路不通"清单，记录试过但没改善甚至变差的改动与原因。它比成功清单更值钱，能防止半年后有人把同一个死胡同再走一遍。

### 9_4 案例小故事：优化了半天，热路径根本不在这儿

一次接口延迟偏高，有人立刻把 JSON 序列化换成手写拼接，代码复杂了一大截，压测数字几乎没动。后来按流程跑了一遍 `pprof`，CPU 大头竟然落在一个不起眼的日志格式化调用上：每条请求都拼了一条带完整上下文的字符串，而其中一次反射取值被反复执行。

真正的改动只有两行：把那条日志降为条件输出，把反射结果缓存。序列化那坨手写代码被整体回退。复测后 `ns/op` 明显下降，`B/op` 也跟着降，且三轮重复测量趋势一致。

复盘时最被强调的不是那两行代码，而是那张基线表：它让"没改善"这件事当场可见，避免了继续往错方向加码。团队由此定下一条规矩——性能改动若拿不出改动前后同样命令下的数值，评审直接退回；"此路不通"也要写成一张卡归档。这条规矩在板块12 被并入交付检查单。

### 9_5 实用验证：命令、预期与判定

```bash
go test -bench=BenchmarkHot -benchmem -count=3 -cpuprofile=cpu.out ./...
go tool pprof -top cpu.out
go test -bench=BenchmarkHot -memprofile=mem.out ./...
go tool pprof -alloc_space -top mem.out
go build -gcflags=-m ./... 2>&1 | grep "escapes to heap"
GODEBUG=gctrace=1 ./bin/app
```

预期：三轮基准数值波动在可接受范围；`pprof -top` 能明确指出耗时或分配占比最高的函数；逃逸输出中能对应到具体变量；`gctrace` 打印出含堆大小与暂停时间的行。

判定：改动前后用同一命令、同一输入规模、同一台机器各跑三轮，取中位数对照。改善方向符合"预期"字段且三轮趋势一致记"通过"。加一道反向验证：把优化改动回退，数值应回到基线附近；回不去说明环境变了或测量有污染，本次结论作废重测。

### 9_6 常见误区与进阶钩子

「1」误区：用一次运行结果下结论。基准至少三轮取中位数，注意 CPU 频率与后台负载。
「2」误区：把 `sync.Pool` 当长生命周期缓存。它的内容可能在任意 GC 时被清理，只适合复用临时对象。
「3」误区：为了"减少 GC"盲目调大 `GOGC`。先看分配速率，堆峰值与暂停都要一起看。
「4」误区：在基准里造一个与真实负载形状完全不同的输入。输入规模与分布必须来自真实场景。
「5」进阶钩子：抓一份 `runtime/trace`，用 `go tool trace` 观察 goroutine 阻塞与调度延迟，把它与 CPU profile 的结论对照，若两者指向不同瓶颈，把差异写成一张场景卡。
