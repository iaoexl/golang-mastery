## 板块11 · 进阶边界：反射、泛型约束、代码生成与红线

### 11_1 核心机理与关键概念

板块10 把外部不确定性挡住，板块11 处理语言里那些"能力很强但代价很高"的工具。精通的标志不是会用它们，而是知道什么时候不该用。

`reflect` 让程序在运行时查看与构造类型，适合写通用编解码、ORM 映射、测试断言这类框架代码；代价是类型错误推迟到运行时、性能明显下降、可读性变差，且编译器无法帮你兜底。业务代码里出现 `reflect`，先问一句"能否用泛型或接口替代"。

泛型约束进阶的重点是"用约束精确描述类型集合"：自定义约束接口、类型集合的并集与近似类型、以及实例化时的类型推断边界；约束写得越窄，调用方越安全。

`go generate` 与构建标签属于"编译前的能力"：前者把重复代码交给生成器产出，后者按平台或特性开关选择文件。`unsafe` 与 `cgo` 是最后的红线——跨过它就要自己承担内存安全、跨平台与构建复杂度；

除非有明确的性能或互操作证据，否则不进入业务代码。把这些工具按"安全代价"排成一列，决策就有了刻度。

```text
  低代价                                          高代价
  接口/组合 -> 泛型约束 -> 代码生成 -> reflect -> unsafe/cgo
     |            |           |           |           |
  编译期检查   编译期检查   生成后可查  运行时才查   自己担责
  首选         次选         重复代码     框架内部     需书面理由
```

阶梯上的每一级都有可以写进评审清单的具体判据，而不是靠"感觉风险大不大"。

`reflect` 最容易翻车的是"能读不能改"：一个值只有**可寻址且可被设置**时才能赋值，从接口里取出的值通常不可寻址，必须先传指针、再取 `Elem()`。下面这条判定链应当能背出来，因为它对应的 panic 文案在运行时才出现，编译器一句都不会提醒。

```text
  reflect.ValueOf(x)
        |
        v
  Kind() 是什么  -> 区分基础种类，不能当成类型相等判断
        |
        v
  CanAddr() 为真? --否--> 不可取地址，赋值必然 panic
        | 是
        v
  CanSet() 为真? --否--> 从不可导出字段或接口副本取出，赋值必然 panic
        | 是
        v
  Set*() / 按 Kind 选具体 Setter
```

| 判据 | 正确写法 | 运行时症状 |
| --- | --- | --- |
| 传值还是传指针 | 要改就传指针并 `Elem()` | 赋值时 panic，提示不可设置 |
| `Kind` 与 `Type` | `Kind` 判种类、`Type` 判具体类型 | 把具名类型当基础种类，分支走偏 |
| 零值与 nil 接口 | 先判 `IsValid()` 再取 `Kind()` | 对无效值调用方法直接 panic |
| 可导出性 | 跨包字段必须大写开头 | 读得到但设不了，且不报错 |

代码生成与构建标签的共同要求是**可复现**：生成物能被同一条命令原样重造，才允许提交；否则手改一次，下次生成就把它悄悄覆盖掉。

| 机制 | 写法要点 | 复现判据 |
| --- | --- | --- |
| `go:generate` 指令 | 写在 Go 文件里，指明生成器与参数 | 删掉生成物后 `go generate ./...` 能重建且差异为空 |
| 构建约束 `go:build` | 文件顶部，条件可用与或组合 | 两份平台实现分别交叉编译，选中文件不同 |
| 文件命名后缀 | 按系统或架构自动筛选 | 不需要额外声明，但改名即失效 |
| `embed` | 把静态资源编进产物 | 路径相对当前文件，漏文件在编译期报错 |
| 生成物标记 | 首行写明"请勿手改" | 门禁里比对生成前后差异 |

旧式 `+build` 注释与新式 `go:build` 不要混写，两者条件不一致时行为很难查；同一文件只用一种。`go generate` 也不会自动执行，必须显式调用，因此"本地能编、CI 编不过"最常见的原因就是有人改了源文件却没重跑生成器。

`unsafe` 与 `cgo` 的代价要写具体，才能判断"值不值"：

| 工具 | 换来的能力 | 必须承担的代价 |
| --- | --- | --- |
| `unsafe.Pointer` | 绕过类型系统做零拷贝转换 | 转换须在一次表达式内完成；把 `uintptr` 存成变量再转回，GC 移动或回收后就是悬垂指针 |
| `unsafe.Sizeof` 等 | 观测布局、偏移量 | 结果依赖平台与编译器，不能写进对外协议 |
| `cgo` | 调用既有 C 库 | 交叉编译需要对应平台工具链；C 侧内存 GC 看不见；每次调用有额外开销 |
| `//go:linkname` 等编译器指令 | 触及运行时内部符号 | 编译器版本一变即可能失效，且绕过 `vet` 的多数检查 |

因此红线登记表里"理由"一栏不能只写"性能更好"，必须附一组基准数值与"接口/泛型/生成代码都试过且不可行"的结论。没有数值，就没有例外。

### 11_2 可落地操作清单

第1步：挑一段用 `reflect` 写的通用逻辑，尝试用泛型改写，对比行数与编译期报错能力。
第2步：定义一个自定义约束，让一个不满足约束的类型传入，记录编译报错首行。
第3步：写一个 `go generate` 指令，由生成器产出一份重复代码；删掉生成物后再跑一次 `go generate ./...`，确认版本库差异为空且带"请勿手改"注释。
第4步：用构建标签为两个平台各放一份实现文件，分别交叉编译，验证选中的文件不同；同一文件不要混写新旧两种约束写法。
第5步：写一段故意对不可设置值赋最小片段，把 panic 原文与 `CanAddr`/`CanSet` 两项取值一起记进红线卡。
第6步：找出项目里所有 `reflect`、`unsafe`、`cgo` 的出现位置，逐处写一句带基准数值的理由；再执行 `go vet ./...` 与 `go test -race ./...`，确认门禁仍全绿。

### 11_3 场景笔记法：边界工具的取舍留痕

这类笔记的目的是防止"当时图快、事后没人敢动"，所以用红线卡把理由强制写下来。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明要解决的问题、考虑过的低代价替代方案 |
| 预期 | "替代方案不可行或有可量化证据；引入后门禁仍全绿" |
| 动作 | 贴出关键片段与 `go generate` / 构建标签命令 |
| 观察 | 粘贴编译报错、生成物差异、基准数值或交叉编译结果 |
| 判定 | 理由成立且可复现记"通过"；只写"方便"记"待查"并回退 |
| 迁移 | "凡出现红线工具，代码旁必须有指向这张卡的链接或注释" |

实用补充：维护一张"红线登记表"，逐行记录文件位置、工具类型、理由、复核人、复核结论。每次评审只扫这张表，不必全文搜索。

### 11_4 案例小故事：一个反射工具让全组停了半天

有人为了少写几行，在业务层封装了一个"任意结构体转查询条件"的反射工具，用起来确实省事。直到某天一个字段从值类型改成指针类型，编译安然通过，运行时却在生产环境悄悄生成了错误的查询条件，且没有任何报错。排查半天，最后靠对比日志里的条件串才定位到。

处理方式分两步：短期把那段逻辑改成显式泛型函数，让类型不匹配在编译期就红；长期在评审清单里加一条——业务目录出现 `reflect`，必须附一张红线卡，写清"为什么接口与泛型都不行"。那个反射工具没有删，而是收进框架层，并补了覆盖类型变更的测试用例。

有意思的是，这次复盘让大家反而更敢用高级工具了：不是因为放开限制，而是因为每条例外都有理由、有测试、有归档。板块12 的反模式清单里，这条被写成"把运行时错误留给自己，把编译期检查交给别人"。

### 11_5 实用验证：命令、预期与判定

```bash
go generate ./...
go vet ./...
go test -race ./...
GOOS=linux GOARCH=amd64 go build ./...
GOOS=windows GOARCH=amd64 go build ./...
go test -bench=. -benchmem ./...
```

预期：生成物可编译且含"请勿手改"标记，删掉后重跑生成，版本库差异为空；两个平台交叉编译各选中对应的构建标签文件；不满足约束的类型在编译期报错而非运行时；对不可设置值赋值的片段稳定 panic 且 `CanSet` 为 false；

泛型版相对反射版在基准里 `ns/op` 更优或至少不劣；`-race` 与 `vet` 全绿。

判定：做四次主动破坏——传入不满足约束的类型、删掉生成物后不重跑 generate、故意让构建标签拼写不一致、把 `uintptr` 存成变量再转回指针，四次都应被编译期或门禁抓住。全部抓住记"通过"。

再核对红线登记表：每一处 `reflect`/`unsafe`/`cgo` 都有理由、基准数值与复核结论，只写"方便"或缺数值记"待查"并回退。

### 11_6 常见误区与进阶钩子

「1」误区：用 `reflect` 规避类型设计。先问能否用接口或泛型，把类型错误留在编译期。
「2」误区：泛型约束写成 `any`，等于把类型检查又推回运行时。用约束把集合说窄。
「3」误区：把生成物手改后直接提交。加醒目标记，并在门禁里检查生成前后差异。
「4」误区：为"可能以后要跨平台"提前引入 `cgo`。没有明确互操作需求就不跨这条线。
「5」误区：把 `unsafe.Pointer` 转成 `uintptr` 后存进变量、过几行再转回。GC 不把它当指针看，对象一旦移动或回收就是悬垂指针；转换必须在一次表达式内完成。
「6」误区：同一文件混写 `go:build` 与旧式 `+build`，或把生成物手改后直接提交。统一只用一种约束写法，并在门禁里比对生成前后差异。
「7」误区：用 `reflect.Kind()` 判断具体类型相等，或忽略 `IsValid()` 直接对零值取种类。前者分支走偏，后者运行时 panic。
「8」误区：红线登记表里只写"为性能"三个字。没有基准数值与"低代价方案都试过"的结论，就不构成例外。
「9」进阶钩子：用 `go doc` 通读 `reflect` 包关于可设置性与可寻址性的说明，写一段故意触发 panic 的最小片段，把 panic 原文与原因写进红线卡，作为"运行时才查"的实证。
