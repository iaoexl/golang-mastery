## 板块0 · 总纲：学习路径与边界

### 0_1 学习路径

路径按"能力闭环"划分，不按日历划分。每阶段只有一个硬门槛：该阶段的通关验证必须跑通。

| 阶段 | 对应板块 | 主线任务 | 产出物 | 通关验证 |
| --- | --- | --- | --- | --- |
| 阶段一 · 能跑 | 板块1至板块2 | 工具链、模块、基础类型、控制流、错误即值 | 一个可 `go run` 且 `go test` 全绿的命令行小程序 | `go vet ./...` 无告警，测试通过 |
| 阶段二 · 懂内存 | 板块3 | 切片底层数组、map、结构体、指针、逃逸 | 一张自己画的内存草图 + 一段无别名 bug 的数据处理代码 | 附加 `go test -race` 通过 |
| 阶段三 · 会抽象 | 板块4 | 方法集、隐式接口、最小接口、泛型约束 | 一个可替换实现的小组件（内存版与文件版） | 换实现不改调用方，测试仍全绿 |
| 阶段四 · 能并发 | 板块5 | goroutine 生命周期、channel 关闭规则、context 取消 | 一个可超时、可取消、可优雅退出的管道 | 压测下无 goroutine 泄漏 |
| 阶段五 · 可交付 | 板块6至板块8 | 依赖锁定、项目布局、标准库实战、质量门禁、日志与指标 | 一个带健康检查的服务、构建产物与全绿门禁记录 | 交叉编译成功，干净环境重建与门禁全绿 |
| 阶段六 · 能精进 | 板块9至板块11 | 基准、逃逸分析、pprof、GC 观测、系统边界、进阶边界工具取舍 | 一份前后对比的性能基线表与红线登记表 | 指标改善有数值且可复现，红线均有书面理由 |
| 阶段七 · 收口 | 板块12 | 反模式清单、评审检查单、交付演练 | 一份自己的通关记录 | 12_5 总验收全项通过 |

阶段与板块严格按编号区间对齐，板块1至板块12 全部有归属，无遗漏。阶段之间的过渡不是"学完就翻页"，而是"上一个产出物成为下一个的输入"：阶段三写出的可替换组件，在阶段五会被换成真实存储实现；阶段六的基准数据来自阶段五那个服务，而不是凭空造的玩具函数。

```text
  能跑 -> 懂内存 -> 会抽象 -> 能并发 -> 可交付 -> 能精进 -> 收口
    |        |         |         |         |         |        |
  最小闭环  内存草图  可替换件  可取消管道  健康服务  基线表  通关记录
```

#### 三级刻度与七阶段的对齐

七阶段按能力闭环推进，三级按能力刻度收拢，互不替代。每一块正课都落在某一级里，没有"学完却不算数"的悬空板块。

| 层级 | 覆盖阶段 | 覆盖板块 | 这一级真正要拿到的东西 |
| --- | --- | --- | --- |
| 入门 | 阶段一至阶段三 | 板块1 至板块4 | 能从空目录起项目，能解释值与内存，能替换实现 |
| 进阶 | 阶段四至阶段五 | 板块5 至板块8 | 能写可取消的并发管道，能锁依赖、搭服务、过门禁 |
| 精通 | 阶段六至阶段七 | 板块9 至板块12 | 能用数值定位瓶颈，能守边界，能交付并回滚 |

详细晋级判据见 README_8。

### 0_2 使用建议与边界声明

「1」本册聚焦 Go 语言本身的语言机制、标准库用法与工程实践；不覆盖特定业务领域的算法推导与领域建模，遇到领域问题应以该领域的权威资料为准。
「2」示例以标准工具链与标准库可直接复现为准；涉及第三方组件时只描述接口契约与验证方式，不假定特定版本的行为永远不变。
「3」命令、输出与判定标准以你自己机器上实际跑出的结果为准。不同工具链版本在提示文案与默认参数上存在差异，遇到不一致时以 `go doc` 与本地输出为准，而不是照抄本册的示例输出。
「4」学习节奏用相对阶段表达，不设定具体年份、季度或日期，也不承诺某个时点必须达到某个水平；进度只看验证通过率。
「5」笔记法不是附加装饰。每个板块的 X_3 都给出该场景专用的记录模板，若跳过记录，X_5 的验证就失去了可追溯的对照基准。
「6」边界之外的内容（如特定框架源码、特定云厂商部署细节）应以官方文档为准；本册提供的是可迁移的判断框架与验证方法。
「7」工具链支持状态、证书信任基础与镜像层内容属于高频变动信息，本册只给判断框架与验证动作，不写死任何版本号或日期；遇到安全公告、终止支持或行为变更，以官方渠道的当前说明为准，并把核对结果记进场景卡。

### 0_3 环境基线自检

在动笔写任何业务代码前，先把基线固定下来，后续所有"环境背锅"的争论都能用这张表一秒裁决。

| 检查项 | 命令 | 通过标准 |
| --- | --- | --- |
| 工具链可用 | `go version` | 输出版本标识，无 command not found |
| 模块模式开启 | `go env GO111MODULE` | 为空或 `on`，不要退回旧工作区模式 |
| 缓存路径可写 | `go env GOMODCACHE` 后尝试写入测试文件 | 路径存在且可写 |
| 格式化可用 | `gofmt -l .` | 无输出（或输出的文件被立即格式化） |
| 静态检查可用 | `go vet ./...` | 退出码为 0 |
| 竞态检测可用 | `go test -race ./...` | 能正常编译并运行，不报工具链缺失 |

把六项结果原样粘贴进场景卡的"观察"字段，判定写"基线通过"。这张卡在整个学习周期里只需建一次，但每次换机器、换容器镜像都要重跑一遍。

### 0_4 外部资料与社区的取用口径

起步最常见的弯路，是同时打开十几个教程，却连一个最小闭环都没跑完。资料按用途分层，每层只留一个主入口、一个备用入口；下列代表入口是检索起点，不是背书，也不构成版本依据。

| 用途层 | 代表入口 | 取用方式 | 记进场景卡的内容 |
| --- | --- | --- | --- |
| 权威口径 | 官方文档、英文文档、中文文档、标准库中文版、Go 指南 | 行为有差异时第一顺位查证 | 查了哪一条、本地输出是否一致 |
| 零配置试跑 | Go Tour | 只在浏览器里建立手感，不替代本机闭环 | 试跑结论与本机构建结果的差异 |
| 系统入门 | 菜鸟教程、W3Cschool、易百教程 | 选一套主线读完基础，其余只查单点 | 进度用验证通过率记，不用页数记 |
| 按例速查 | Go by Example | 一个知识点配一段能跑通的小例子 | 例子里与本册结论冲突之处 |
| 练习与自检 | 社区面试题、每日一学 | 每个知识点配一道能判分的题 | 错题归入反例清单 |
| 问答排障 | Stack Overflow、Go Forum | 先搜再问，提问附最小可复现片段 | 问题要点、采纳结论、本地复跑结果 |
| 中文社区 | Go语言中文网、LearnKu、GoCN Forum、golang 吧 | 读节点导航与按主题归档的技术版块 | 可迁移的规范或设计取舍 |
| 设计哲学 | Go Forum | 查标准库取舍、编程规范与设计理由 | 一条结论配一处代码对照 |
| 开源阅读 | GitHub 上的议题与变更 | 通过议题和变更记录看真实决策过程 | 取舍理由与可复用写法 |

```text
  官方口径 -> 互动试跑 -> 系统教程 -> 按例速查 -> 练习自检
      |                                            |
      +------------------> 本地复跑 <---------------+
                              |
                              v
                    场景卡(观察/判定/迁移)
                              ^
                              |
              问答社区 / 中文社区 / 开源议题
               (先过滤杂项，再取结论)
```

三条取用纪律：

「1」第1步先用权威口径定结论，再用教程与例站补手感；两者冲突时以本地实际输出与官方说明为准，不照抄示例输出。
「2」第2步对社区页面做资料甄别：导航分类、官方文档入口、按主题归档的技术节点属于有效信息；推广、重复发布的无信息帖、与语言主题无关的源码交易和广告属于杂项，不进笔记、不进卡片库。
「3」第3步提问与讨论守住协作底线：不人身攻击、与人为善；先给最小可复现片段与已跑过的验证，再描述差异，对方给的结论在本地复跑一遍才归档。

版本与信任基础单独按一条口径处理。工具链、证书信任包、基础镜像、存量构建缓存都可能出现"代码没变、信任基础变了"的情况，这类信息不写死任何版本号或日期，只固化成可复跑的动作：核对当前工具链是否仍在官方支持范围内；重建容器镜像时禁用层缓存以拉取最新基础层；

在干净环境复跑 `go mod verify` 与全部门禁，不因本机缓存命中就判定通过。把每次核对的本地输出贴进场景卡的"观察"字段，判定只写"与官方当前说明一致"或"待迁移"。

对应到本册：查证动作落在 2_3 的假设—反例卡，依赖与产物核对落在 6_3 的决策卡，信任基础变更落在 10_3 的边界演练清单，最终在 12_3 统一归档。

把三类常见外部资料落成资料取用卡，可以直接照着填：

| 资料类型 | 只取什么 | 明确不取什么 | 归档到哪 |
| --- | --- | --- | --- |
| 安全公告类 | 四个可复跑动作：核对支持状态、清点存量构建环境、禁用层缓存重建、干净环境复跑门禁 | 公告里的具体版本号、日期、外链安装命令 | 10_3 边界演练清单 |
| 社区发言规范类 | 提问纪律：先给最小可复现片段与已跑过的验证，再描述差异 | 情绪化争论、人身攻击、无证据的结论 | 0_4 资料取用卡 |
| 社区聚合页类 | 节点导航、官方文档入口、按主题归档的技术版块 | 推广、重复发布的无信息帖、与语言主题无关的源码交易与广告 | 12_3 资料取用卡 |

判定只写"与官方当前说明一致"或"待迁移"；写不出这两句，说明还在抄结论而不是做验证。配套实战工程的门禁脚本与回滚演练脚本把这些动作固化成可重跑的命令，而不是留在笔记里的一句话。

#### 信任链变更的四类对象

安全公告类资料最容易抄错的，是把"某个包的版本号"当成结论。可迁移的是下面这张表：证书信任包、包管理器、基础镜像、存量构建环境各自会怎么变、各自怎么验。业务代码一行没改，TLS 客户端的前提也可能已经变了。

| 对象 | 会怎么变 | 可复跑动作 | 判定 |
| --- | --- | --- | --- |
| 证书信任包 | 根或中间证书被移除、信任列表调整 | 在干净环境复跑一次外部请求与门禁 | 与官方当前说明一致 / 待迁移 |
| 包管理器与安装器 | 自身携带的信任配置随更新变化 | 清点所有存量环境并逐一更新，不复用旧缓存 | 全部环境均已核对 |
| 基础镜像与层缓存 | 旧层里仍是旧的证书集合 | 重建时禁用层缓存，明确拒绝旧层 | 新层被实际拉取 |
| 存量构建环境 | 本机缓存命中掩盖了前提变化 | 空目录重跑 `go mod verify` 与全部门禁 | 差异为零且全部通过 |

#### 存量构建环境的清点动作

"清点所有存量环境并逐一更新"如果只写成一句原则，执行时最容易只更新当前终端里那一个。把它拆成四步，每一步都留可粘贴的输出。

| 步 | 动作 | 该看的输出 | 判定 |
| --- | --- | --- | --- |
| 第1步 | 列出本机所有工具链根目录与模块工作区，不要只看当前终端 | 每个根目录的路径与来源 | 清单完整，没有"想不起来在哪装过"的项 |
| 第2步 | 对每个根目录分别打印工具链版本与环境变量摘要 | `go version`、`go env` 的关键行 | 每个条目都能说出它属于哪个项目 |
| 第3步 | 在不复用旧缓存的空目录里，对每个环境各跑一次只读校验与门禁 | `go mod verify` 与门禁逐条结果 | 全部通过，差异为零 |
| 第4步 | 把清单、逐条输出与"已核对 / 待迁移"写进场景卡 | 一张带最后复核列的核对表 | 没有只写"环境没问题"的合并结论 |

常见误判是把"本机缓存命中"当成"前提未变"：缓存会让旧配置继续看起来正常。第3步必须换空目录，目的正是让缓存无法替你作答。工具链支持状态与证书链分开判定，前者写"待迁移"，后者写"与官方当前说明一致"，不合并。

Go 侧还有一条独立判据：工具链本身是否仍在支持范围内，与上面四类对象不是同一件事。前者决定"该不该继续在这个分支上加固"，后者决定"这次连接还可信"。两条都写进场景卡，但分开判定，不合并成一句"环境没问题"。
